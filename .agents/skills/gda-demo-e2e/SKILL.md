# Demo 端到端验收

以 `demo/` 下某个工程为场地，用 GDA 完成一轮真实开发或验收，并把过程、问题与优化建议沉淀成报告。本轮同时是 GDA 递归优化闭环的一圈：只做在线探索与证据沉淀，不改 GDA 本体。

## 输入

- 必填：demo 标识。接受 `pink_man_adventure` 与 `demo/pink_man_adventure` 两种写法。
- 可选：本轮聚焦目标（例如「只验证场景与脚本工具」）。未给出时按 demo 的任务书完整推进。
- 未指定 demo 时，列出 `demo/*` 目录并停止，等待选择；不得默认选一个开跑。

## 1. 解析与校验

1. 规范化到 `<repo>/demo/<name>`。
2. 校验 `project.godot` 存在；不存在则报错并列出可用 demo，停止。
3. 校验 `docs/` 存在；不存在时只做运行与观测验收，并在报告中标明无设计文档。

## 2. 读任务书

按顺序读取，后面的文档不覆盖前面的硬约束：

1. `docs/README.md`：项目说明与阅读路径。
2. `docs/test/test-plan.md`：任务性质、测试约定、证据要求、问题格式、终止条件。
3. `docs/test/acceptance.md`：验收清单。
4. 按 test-plan 的阅读路径补读 `docs/gdd/`、`docs/tech/`、`docs/art/` 中与本轮相关的页面。
5. 若 `report/<demo>/` 最近一轮存在 `analysis.md`，读取其中的「待下一轮端到端验证项」作为本轮附加观察点；该文件缺失时不报错、不阻塞，也不改变本轮 test-plan。

判定任务形态：

- 开发型：工程为空或文档要求从零实现。工程文件的创建与修改仅经 GDA。
- 验收型：工程已建成，test-plan 要求只读运行与核对。工程文件只读。

demo 文档中的项目约定优先于本技能的默认流程；两者冲突时，在报告中记录冲突并以 demo 文档为准。

素材与资源位置以 demo 文档为准，不假设固定目录。开发型允许只读查阅 `*.tscn`、`*.tres`、`project.godot` 等工程文件用于核对与截图验证，但不得手动修改。

## 3. 前置检查

1. 确认 `addons/godot-autopilot/` 已部署。缺失时在仓库根执行：
   - `uv run main.py build`
   - `uv run main.py deploy --demos <name>`
2. 确认 GDA MCP 可达：调用 `system_status`，要求返回 `running=true`。不可达时停止，说明需要打开 Godot 编辑器并启用插件；部署后仍不可达时请用户重新打开工程或启用插件。不得自行启动或重启 Godot。
3. 记录基线：开始时间、`system_status.version`、`get_engine_version`、`git rev-parse --short HEAD`。
4. 定位本轮轨迹：用 `execute_script` 读取 `GODOT_AUTOPILOT_TRACE_DIR` 与 `GODOT_AUTOPILOT_LOG_DIR`。被授权门拒绝时，记录「轨迹不可得」及原因，继续执行，不推测。
5. 工具名与参数以 `search_tools` 的返回为准，不凭记忆调用。

## 4. 执行

1. 按 demo 的 test-plan 推进；无 test-plan 时按「搭 → 写 → 看 → 定」四拍推进，先搭场景与调整，再写脚本与挂载，再运行调试，据结果进入下一轮。
2. 单环只做一个功能增量，不把多个功能合并到同一环。
3. 每环开始前记录基线：同条件截图、读回值或日志。
4. 每环的「看」必须产生证据：结构类用编辑器截图，运行类用游戏截图；逻辑类可用读回值或日志。
5. 改动后用与基线相同的条件复测，记录行为差异；只写「通过」不算对照，必须有基线 vs 改动后的可比证据。
6. 失败时区分「改动无效」与「引入回归」；引入回归的改动回退本环。
7. 本环验收项全过才进入下一环；失败只回滚本环，不扩大范围。
8. 手感与数值问题当场微调并复验，不带病进入下一环。
9. 本轮聚焦目标存在时，优先覆盖该目标，但仍需交付一个可运行、可复验的增量。

## 5. 过程记录

1. 开始执行前创建本轮目录（路径见第 8 节）与其中的 `report.md`，先写标题、基本信息与「执行过程」标题。
2. 每环结束立即在「执行过程」追加一段：环号、目标、基线证据、关键动作、改动后证据、行为差异、截图相对路径、发现的问题。
3. 报告随做随写，不得在结束后凭印象补写。
4. 轨迹已由 GDA 自动记录，不抄录全量调用序列；只摘录支撑结论的关键事件（工具名、参数摘要、ok、error_code、duration_ms、request_id）。

## 6. 证据

| 证据 | 来源 | 用途 |
|---|---|---|
| GDA 轨迹 `trace-*.jsonl` | `GODOT_AUTOPILOT_TRACE_DIR` | 调用序列、耗时、错误码、参数摘要 |
| GDA 日志 `gda-*.log` | `GODOT_AUTOPILOT_LOG_DIR` | 人类可读的失败上下文 |
| 截图 | 本轮目录 `img/` | 结构、画面、菜单与行为 |
| 读回值 | 工具返回 | 逻辑断言 |
| 对照证据 | 基线 vs 改动后的成对截图/读回值/日志 | 证明行为差异，区分修复与回归 |

- 轨迹默认脱敏：参数截断到 4000 字符、敏感键替换；截图默认不写入轨迹。报告中注明这一点。
- 轨迹保留最近 20 文件 / 50MB。结束前把本轮关键事件摘录到本轮目录 `evidence.md`：工具名、参数摘要、ok、error_code、duration_ms、request_id、对应截图。不复制完整 `trace-*.jsonl` 与 `gda-*.log`。
- 原始轨迹与日志路径记录在报告与 `evidence.md` 中，用 `<集中根>/projects/...` 占位，不写真实用户名或本机绝对路径。
- 报告与 `evidence.md` 引用截图使用相对路径；原始轨迹/日志只作可追溯来源，不要求轮目录内存在副本。
- 涉及画面效果的验收必须看图，逻辑断言不能替代截图。

## 7. 评估

以资深使用者与开发者视角评估 GDA，既记录不足，也记录良好表现；不找茬、不夸大。影响推进的负面表现必须在第 4 节登记为带编号的问题条目；第 3 节只做归纳，不留下无法追溯的结论。

参考维度（按需选用，无发现可跳过，不凑数）：

现有工具与 Skill 优化、工具完备性、参数与数据合理性、日志、步骤合并/快捷工具、错误处理与恢复、性能与效率、一致性与幂等性、可发现性与文档、可组合性与工作流、上下文感知与状态管理、安全与权限、兼容性与版本适配、可测试性与验证、可视化与反馈、可扩展性、资源/场景/脚本操作覆盖、版本控制友好、任务规划与自主性、与 Godot 原生工作流对比、工具粒度与依赖、返回值结构化与机器可读。

每条问题带唯一编号 `Q1`、`Q2`…，并标注类型：失败 / 缺陷 / 体验 / 文档；同时标注可复用性：通用 / 本工程。通用指换一个 demo 仍可复现；本工程指仅在当前 demo、当前环境或本次会话出现。编号在本轮内唯一且连续。

每个问题记录包含五要素：

1. 触发场景
2. 详细操作步骤
3. 预期行为
4. 实际表现（附证据）
5. 问题分析（无法定位根因时写明边界）

问题条目格式：

```markdown
### Q1 [失败] <一句话标题>
- 触发场景：
- 操作步骤：
- 预期行为：
- 实际表现：
- 问题分析：
- 可复用性：通用 | 本工程
- trace：`<文件名>#seq=<n> | <tool> | ok=<bool> | error_code=<...> | duration_ms=<...> | request_id=<...>`
- 截图：`img/<文件名>`
```

## 8. 报告

- 本轮目录：`report/<demo>/<YYYY-MM-DD-HH-mm>/`，时间取本地开始时间；目录已存在时追加 `-2`、`-3`，不覆盖已有轮次。
- 报告：本轮目录下的 `report.md`（目录已带时间，文件名固定）。
- 资源：本轮目录下的 `img/`（截图）、`evidence.md`（关键事件摘录）。其他本轮产物同样放本轮目录，不写入共享目录。
- 本轮目录自包含报告、截图与关键事件摘录；原始轨迹/日志只记录路径，不复制完整文件。
- 写入边界：本轮只写 `report.md`、`evidence.md`、`img/`；不创建、不改写 `analysis.md`；本轮结束后不再改写这些文件。
- demo 文档若写 `report/<ts>-report.md` 或 `report/img/`，以本技能路径为准，并在报告中说明覆盖。
- 报告结构：

```markdown
# <demo> 端到端测试报告
- 开始时间 / 结束时间 / GDA 版本 / Godot 版本 / git HEAD / 任务类型 / 完成度
- 轨迹：`<集中根>/projects/...`（关键事件见 `evidence.md`）
- 日志：`<集中根>/projects/...`

## 1. 结论摘要
## 2. 执行过程（每环一段，随做随写）
## 3. GDA 工具表现评估（按选用的维度）
## 4. 问题记录（Q1、Q2…；类型 + 可复用性 + 五要素 + trace 引用 + 截图）
## 5. 优化建议（S1、S2…；按优先级，每条含实际收益、触发场景、验证方式）
## 6. 递归闭环产出（经验条目、优化提案、验证方式、下轮建议）
## 7. 通用事实 vs 本工程偶然现象
## 8. 证据索引（截图、trace/log 路径、未覆盖项）
```

每条优化建议编号 `S1`、`S2`…，便于后续逐项评估。优化建议只写满足以下全部条件的条目：

- 当前开发实际遇到并影响推进；
- 能说明实际收益与触发场景；
- 能说明验证方式；
- 不是过度设计或理论上的「最好有」。

优先级：阻塞开发 > 显著降低效率 > 影响结果正确性 > 提升长期可维护性。

## 9. 递归优化闭环

闭环按「在线探索 → 证据沉淀 → 离线评估 → 部署改进」推进，改进对象是 GDA 工具集与技能，不是被测工程。

- 本轮执行「在线探索」与「证据沉淀」：真实开发动作 + 轨迹 + 报告。
- 「离线评估」与「部署改进」属于后续轮次，需要用户明确授权；本轮不得自行修改 `src/`、`skills/`、`.agents/skills/` 或配置。
- 离线评估以现役工具集与技能为基线，基线必须留在候选集内；候选方案只有在同一批历史证据上不劣于基线才可采纳，否则回退基线。
- 部署改进只落胜出方案，并保留回归基线，确认不破坏既有功能。
- 证据池是 `report/` 下所有 demo 的轮目录，跨轮累积；每轮目录自包含报告、截图、关键事件摘录、对照证据与后续 `analysis.md`（若存在），不与其他轮共用资源；不新建索引文件。
- 每轮结束向证据池新增一条可回放记录：本轮 `report.md`、`evidence.md`、关键对照（Q 编号与基线/改动后差异）、`analysis.md`（若存在）。历史证据不足时，后续分析用最小复现代替回放，并在报告中注明。
- 报告第 7 节区分两类结论：
  - GDA 通用事实：换 demo 或工程仍成立，写明复现条件。
  - 本工程偶然现象：仅在本 demo、本次会话或当前环境出现，写明未跨工程验证。

## 文件契约（自包含）

本技能只通过文件系统与后续流程配合，不依赖任何其他技能。

- 输入：`demo/<name>/`、`docs/`、同一 demo 的历史轮目录（可选）。
- 输出：`report/<demo>/<YYYY-MM-DD-HH-mm>/report.md`、同目录 `evidence.md`、`img/`；每环的基线/改动后对照证据。
- 可选读取：同 demo 最近一轮的 `analysis.md`，只取「待下一轮端到端验证项」。
- 不写：`analysis.md`；不修改已有轮目录中的文件。
- 编号：问题 `Q<n>`，优化建议 `S<n>`；问题标注类型与可复用性（通用/本工程）。
- 回放：每轮提供可回放的报告、证据与对照材料，供后续离线评估；不复制完整轨迹。

## 10. 禁止事项

- 禁止绕过 GDA 手动编辑任何 Godot 工程文件（`*.tscn`、`*.tres`、`*.gd`、`project.godot` 等）。
- 禁止主动重启 Godot；引擎崩溃即停止并如实记录。
- 禁止更新 wiki（`docs/wiki/`）、`AGENTS.md` 或技能文件。
- 禁止编造、夸大或凭印象补写工具表现与调用记录。
- 禁止为凑评估维度硬评，禁止把理论上的「最好有」写成优化建议。
- 禁止提交 git。

## 11. 终止与收尾

立即终止并转入报告的条件：

- GDA 功能缺失或致命缺陷导致无法继续开发；
- Godot 崩溃；
- 前置检查失败且无法在不违反约束的前提下恢复。

收尾检查：

- 轮目录名严格为 `YYYY-MM-DD-HH-mm`（零填充），保证分析侧可按目录名排序取最新；
- 本轮目录自包含报告、截图与关键事件摘录：`report.md`、`img/`、`evidence.md` 齐全，报告内截图引用均为相对路径；
- 报告 8 节齐全，问题均有证据；
- 问题编号唯一、类型与可复用性标注齐全，写入边界未被越界；
- 每环有基线 vs 改动后的成对对照证据，引入回归的改动已回退；
- 证据池已登记本轮可回放材料；
- 截图文件存在且报告中标注对应环号与验收项；
- 原始轨迹/日志路径已记录，关键事件已写入 `evidence.md`；
- 遗留问题、未覆盖项与下一轮建议已写入报告。
