# 报告与问题条目模板

## 问题条目格式

每条问题按五要素记录：触发场景、详细操作步骤、预期行为、实际表现（附证据）、问题分析（只基于本轮可观察证据；阶段 1 盲测不读 GDA 源码补全根因，根因结论标「待分析」交阶段 2）。格式：

```markdown
### Q1 [失败] <一句话标题>
- 触发场景：
- 操作步骤：
- 预期行为：
- 实际表现：
- 问题分析：
- 可复用性：通用 | 本工程
- trace：`<文件名>#seq=<n> | <tool> | ok=<bool> | error_code=<...> | duration_ms=<...> | request_id=<...>`
- 截图：`img/<文件名>`
- 因果三元组：动作=<...>；条件=<...>；后果=<...>
```

优化建议条目格式：

```markdown
### S1 [优先级] <一句话标题>
- 实际收益：
- 触发场景：
- 验证方式：
- 因果三元组：动作=<...>；条件=<...>；后果=<...>
```

引擎崩溃类问题追加以下字段，其余条目不需要：

```markdown
- 崩溃归因：工具导致（写明可疑工具：`<tool>`）| 偶发 | 未定
- 可复现性：可复现（重试再次崩溃）| 不可复现 | 未尝试（附原因）
- 恢复次数：<n>；丢失增量：<描述或「无」>
```

## report.md 结构

```markdown
# 端到端测试报告（多子代理四阶段闭环 / 阶段 1 测试）
- 开始时间 / 结束时间 / GDA 版本 / Godot 版本 / git HEAD / 完成度
- 任务书：固定覆盖任务书 `assets/fixed-task-brief.md`（不抽题）
- 工程路径：`<project-dir>` / 来源：固定沙盒或用户指定
- 轨迹：`<集中根>/cli-traces/trace-YYYYMMDD.jsonl`（关键事件见 `evidence.md`）
- 日志：`<集中根>/projects/...`
- GOAL 终态：`active | paused | budgetLimited | usageLimited | complete | unmet`
- 功能单元数：<n>；机制清单：<...>；净可玩内容：<描述去掉计时器后完成一单元的最少有效操作与耗时>；冷启动无错：是 | 否
- 覆盖口径：`覆盖 <N>/253，有效 <M>，无效触碰 <K>，达标=<是|否>，suspected_gaming=<是|否>（依据：...）`（按本轮真实轨迹起始时间过滤，与 `catalog_total=253` join 统计；只读 `digest.json` 判定，不回写本报告）
- 分域覆盖：`分域覆盖：场景=<达标|缺失|不适用>；资源图像=<...>；音频=<...>；动画=<...>；2D或3D=<...>；脚本=<...>；配置=<...>；运行时=<...>；捕获=<...>；调试=<...>；渲染RID=<...>；批处理=<...>`
- Run 标识：起始时间戳 <ms> + trace_id/run 编号 <...>（所有流程数据来自这一次连续 run）
- 因果三元组：动作 → 条件 → 后果（每环功能增量一条）

## 1. 结论摘要（含功能单元数、机制清单、净可玩内容、GOAL 终态、两行覆盖口径）
## 2. 执行过程（每环一段，随做随写；含每环三问答案与「动作→条件→后果」因果三元组、本环新增覆盖工具与累计覆盖数）
## 3. 功能/玩法闭环验证表（硬验收）+ 单元机制与净可玩内容表
## 4. 分域与覆盖率表（分域必覆盖 + 覆盖 253/253）+ 工具真实操作流程表（三要素列；含无效触碰剔除、未覆盖域原因、`suspected_gaming` 依据）
## 5. 组合链与连锁反应表（C1–C6；工具序列、意图、预期连锁、实际连锁、证据、是否发现连锁缺陷）
## 6. GDA 工具表现评估（按选用的维度）
## 7. 问题记录（Q1、Q2…；类型 + 可复用性 + 五要素 + trace 引用 + 截图 + 因果三元组）
## 8. 优化建议（S1、S2…；按优先级，每条含实际收益、触发场景、验证方式、因果三元组）
## 9. 递归闭环产出（经验条目、优化提案、验证方式、下轮建议；软指标由独立子代理判定）
## 10. 通用事实 vs 本工程偶然现象 + 证据索引（截图、trace/log 路径、未覆盖项）
```

> digest 可解析约定：以上字段名与 Q/S 编号、`功能单元数`、`机制清单`、`净可玩内容`、因果三元组、覆盖表三要素列、两行覆盖口径、`suspected_gaming` 均为固定写法，供 `bun run gda-dev-tools harness digest --round <轮目录>` 解析。`digest.json` 为只读派生品，不改写 `report.md` / `evidence.md`。分域覆盖、净可玩内容、跨 run 一致性、组合链证据若 digest 不解析，由独立子代理复核。

### 因果三元组格式（digest 可解析，第 2 / 5 / 7 / 8 / 9 节共用）

每环功能增量、每条组合链、每条 Q、每条 S、每条经验条目各写一组因果三元组，按固定三段写在同一行：

```text
因果三元组：动作=<触发动作或工具调用>；条件=<复现条件或适用范围>；后果=<实际表现或影响>
```

三段缺任一视为不可解析，补写后再产出报告；只写本轮可观察证据，根因未定时「动作/条件」写「待分析」，不臆断。

### 功能闭环验证表字段（第 3 节，硬验收）

逐项列出基线 → 改动后 → 证据；缺任一项不得声称完成。

| 功能要素 | 基线 | 改动后 | 证据 |
| --- | --- | --- | --- |
| 任务书功能契合 | | | 固定任务书功能单元的具体体现 |
| 核心玩法链（目标→挑战→反馈→结果） | | | |
| 胜利状态 | | | 状态读回 + 文本截图 |
| 失败状态 | | | 状态读回 + 文本截图 |
| 重玩与复位 | | | 复位前后读回值 |
| HUD 实时反馈 | | | 截图 |
| 视听反馈 | | | 已导入资源文件 + 节点引用读回 + 截图/日志；不接受内存态直接赋值 |
| 真实输入闭环 | | | `game_input` 注入 + 成对读回值 |
| 运行稳定性 | | | `get_game_log_entries` |

### 单元机制与净可玩内容表（第 3 节附表，digest 可解析）

至少 3 个功能单元，单元间须有**机制差异**。禁止用纯等待计时器凑时长；逐单元写净可玩内容，不填估算。

| 单元 | 主题/目标 | 本单元核心机制 | 与上一单元的机制差异 | 净可玩内容（去掉计时器后的最少有效操作与耗时） | 通关判据 | 证据 |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | | | — | | | |
| 2 | | | | | | |
| 3 | | | | | | |

表后写两行汇总：
`功能单元数=<n>；机制数=<n>；单元间有机制差异=是/否`。
`净可玩内容检验：每单元有效操作时长占比≥50%=是/否；<列出占比最低的单元及原因>`。

所有流程数据必须来自同一次连续 run，并在第 2 节标注 run 标识（起始时间戳 + trace_id）；跨 run 拼凑判 `suspected_gaming=true`。

### 分域与覆盖率表字段（第 4 节附表）

按实际触达填写；不适用须写明理由（如 2D 主题则 3D 域不适用）。

| 域 | 代表工具（触达的） | 状态（达标/缺失/不适用） | 证据 | 不适用理由 |
| --- | --- | --- | --- | --- |
| 场景与节点 | | | | |
| 资源与图像 | | | | |
| 音频 | | | | |
| 动画与 Tween | | | | |
| 2D 或 3D 核心 | | | | |
| 脚本 | | | | |
| 项目与输入配置 | | | | |
| 运行时与输入 | | | | |
| 捕获与日志 | | | | |
| 调试器与系统 | | | | |
| 渲染与 RID 服务器 | | | | |
| 批处理与脚本执行 | | | | |

图像与音频证据必须体现完整资源链路；仅有「内存态生成后直接赋值给节点」不计该域覆盖。

### 工具真实操作流程表字段（第 4 节）

每个工具一个真实操作流程，不是孤立试探；覆盖数以本轮真实轨迹与 253 canonical 名单 join 为准。前三列即反作弊三要素，必须同时填全；缺任一列判无效触碰并从覆盖中剔除。

| 工具 | 服务于哪个功能 | 真实操作步骤 | 结果证据（读回值或截图） | 是否有效 |
| --- | --- | --- | --- | --- |
| | | | | 有效 / 无效触碰（注明缺失要素） |

表后单列三段：

- 无效触碰：`missing required parameter` 等调用，或三要素缺项者；列工具名、原因与缺失要素，不计有效覆盖。
- 未覆盖工具：列出缺失工具及原因（模态工具需人工值守、仅特定场景适用等）；禁止为凑数盲调用补齐，但禁止把真实适用工具标为不适用来逃避门槛。
- `suspected_gaming` 说明：证据与所声称功能数不匹配、或跨 run 拼凑流程数据时写 `suspected_gaming=true` 并写明依据；该轮覆盖不进经验库。表头口径行固定写：`覆盖 <N>/253，有效 <M>，无效触碰 <K>，达标=<是|否>，suspected_gaming=<是|否>（依据：...）`。

### retest.md 结构（阶段 4）

复测子代理在修复分支上盲测，产出轮目录内 `retest.md`（或新轮 `report.md`），结构与 `report.md` 相同但头部标注「阶段 4 复测」并追加对照结论：

```markdown
# 端到端测试报告（阶段 4 复测）
- 轮次关联：<阶段1轮目录> → <修复分支名 + commit> → 本轮
- 基准：阶段 1 的 report.md / digest.json（路径）
- 覆盖口径：`覆盖 <N>/253，有效 <M>，无效触碰 <K>，达标=<是|否>，suspected_gaming=<是|否>（依据：...）`
- 组合链 C1–C6 复验结果

## 1. 复测结论（失败项是否消失、覆盖是否仍 253/253、是否引入回归）
## 2. 失败项复验对照表（Q 编号 | 阶段1现象 | 修复后现象 | 证据 | 结论：消失/仍存在/新回归）
## 3. 覆盖与组合链复验（沿用第 4/5 节表）
## 4. 新发现项（若有，编新 Q 编号，交下一轮阶段 2，不做根因）
```

复测子代理只记录现象与证据，不做根因分析。复测通过 → 主代理收口并请示合并；未通过 → 带新证据回到阶段 2，不自动回到阶段 3（避免修复子代理自评）。
