# 授权修复、增强设计与验证

当阶段 2 产出经独立审查复核一致的采纳项、进入阶段 3 实施修复时读取本文件。修改源码/技能须用户授权；用户已明确要求直接实施时可跳过确认，仍在报告列出计划。

## 触发与授权

- B 完成后，把采纳清单、候选方案与变更计划告知用户并等待授权；只有「授权实施」或用户已给出明确直接实施指令才进入实施。
- 授权边界：只改本项目源码或本技能；保持 `GODOT_CPP_DIR` 只读，旧协议 SDK 已移除、不再涉及；不提交 git（除非用户明确要求）。
- **分支纪律**：修复子代理在新建的独立 feature 分支上工作，命名 `feature/e2e-fix-<语义短名>`（从 `develop` 拉，kebab-case 语义词，禁止纯编号/占位名）。开工先 `git branch --show-current` 复核已切到该分支；在报告中记录分支名与每个 commit。修复子代理不合并分支到 develop，合并由主代理收口并请示。
- 授权不清、采纳边界不清、修改会破坏现有 API/测试/用户可见行为且未获确认时停止请示。

## 增强设计（按采纳项，按「新功能」而非「修 bug」）

每个采纳项至少说明：

- 组件归属：提示词/技能、guardrail（confirm 与安全边界）、上下文/记忆、工具指引、脚本、子代理、middleware/配置、测试或文档。
- 功能目标与用户可感知的变化。
- 性能：是否减少主线程等待、队列往返、重复扫描或大对象复制。
- 安全性：是否影响 confirm 边界、脱敏、路径校验、导出期拒绝或默认安全姿态（不得静默放宽）。
- 便利性：参数是否更少、返回值是否更可直接用于下一步。
- 体验：错误信息是否可操作、日志是否足够定位、失败是否可恢复。
- 向后兼容：现有 API、工具 schema、返回结构与用户可见行为是否保持不变。
- 最小必要变更：列出拟修改文件、函数与行号范围。
- 可回滚：保留变更文件清单与完整 diff。
- 新增测试：补充单元、集成、CLI 或守卫用例。

## 实施与对照

1. 实施前记录 reference 行为：最小复现的输出、错误码、耗时或现有测试结果，作为对照基线。
2. 优先做历史回放：用 `.handoff/report/` 全部历史轮的报告、evidence 与 Q 条目做离线对照；不重复执行整轮端到端，也不重放真实工具调用。历史证据不足时用最小复现。
3. 只修改本项目源码或本技能；遵守项目硬约束：Godot API 经 CommandQueue 在主线程执行；新增 `.cpp` 双登记；源码禁止注释；默认安全姿态不得静默放宽；不破坏现有 API、测试与用户可见行为。
4. 候选实施后在同一条件下 probe；只在目标失败被修复且未引入回归时采纳，否则回退基线。把当前实现始终留在候选集。
5. 不重跑整轮端到端；需要复现失败时只做最小复现并标注。把改变工具行为的项列入「待下一轮端到端验证项」。

## 最小验证集与全面验收

完成后统一全面验收：

- `bun run gda-dev-tools build`
- `ctest --preset debug -L "guard|unit|boundary"`（守卫 + 单元 + 边界）
- 涉及 CLI 时 `bun test cli/tests`
- 涉及引擎内行为时，把最小复现写入报告「待下一轮端到端验证项」，交后续端到端测试执行

记录验证证据：构建输出、测试通过数、关键日志、`git diff HEAD`。回滚前取得用户确认。实施后维护受影响文档与 wiki；仅分析未改代码时不更新。按共享库规则增量写入有证据支撑的结论，按 verifier 规则记录判定，按 GOAL 规则更新长期实施任务状态。把验证结果追加到 `analysis.md` 第 11/12 节。
