# 报告与问题条目模板

## 问题条目格式

每条问题按五要素记录：触发场景、详细操作步骤、预期行为、实际表现（附证据）、问题分析（只基于本轮可观察证据；不读 GDA 源码补全根因，根因结论标记「待分析」）。格式：

```markdown
### Q1 [失败] <一句话标题>
- 触发场景：
- 操作步骤：
- 预期行为：
- 实际表现：
- 问题分析：
- 可复用性：通用 | 本工程
- trace：`<文件名>#seq=<n> | <tool> | ok=<bool> | error_code=<...> | duration_ms=<...> | request_id=<...>`
- 截图：`img/<文件名>`
- 因果三元组：动作=<...>；条件=<...>；后果=<...>
```

优化建议条目格式：

```markdown
### S1 [优先级] <一句话标题>
- 实际收益：
- 触发场景：
- 验证方式：
- 因果三元组：动作=<...>；条件=<...>；后果=<...>
```

引擎崩溃类问题追加以下字段，其余条目不需要：

```markdown
- 崩溃归因：工具导致（写明可疑工具：`<tool>`）| 偶发 | 未定
- 可复现性：可复现（重试再次崩溃）| 不可复现 | 未尝试（附原因）
- 恢复次数：<n>；丢失增量：<描述或「无」>
```

## report.md 结构（第 8 节）

```markdown
# 端到端测试报告
- 开始时间 / 结束时间 / GDA 版本 / Godot 版本 / git HEAD / 主题 / 完成度
- 项目名 / 工程路径 / 主题 / 来源 / 抽样摘要 / draw_id（若本轮由 `jam e2e` 抽题；外部工程写「无」）
- 轨迹：`<集中根>/cli-traces/trace-YYYYMMDD.jsonl`（关键事件见 `evidence.md`）
- 日志：`<集中根>/projects/...`
- GOAL 终态：`active | paused | budgetLimited | usageLimited | complete | unmet`
- 关卡数：<n>；机制清单：<机制1、机制2、机制3...>；净可玩内容：<描述去掉计时器后完成一关的最少有效操作与耗时>；冷启动无错：是 | 否
- 覆盖口径：`覆盖 <N>/252，有效 <M>，无效触碰 <K>，达标=<是|否>，suspected_gaming=<是|否>（依据：...）`（按本轮真实轨迹起始时间过滤，与 `catalog_total=252` join 统计；只读 `digest.json` 判定，不回写本报告）
- 分域覆盖：`分域覆盖：场景=<达标|缺失|不适用>；资源图像=<...>；音频=<...>；动画=<...>；2D或3D=<...>；脚本=<...>；配置=<...>；运行时=<...>；捕获=<...>；调试=<...>`
- Run 标识：起始时间戳 <ms> + trace_id/run 编号 <...>（所有流程数据来自这一次连续 run）
- 因果三元组：动作 → 条件 → 后果（每环玩法增量一条，见第 2 节与第 8 节）

## 1. 结论摘要（含关卡数、机制清单、净可玩内容、GOAL 终态、两行覆盖口径）
## 2. 执行过程（每环一段，随做随写；含每环三问答案与「动作→条件→后果」因果三元组、本环新增覆盖工具与累计覆盖数）
## 3. 玩法闭环验证表（硬验收）+ 关卡机制与净可玩内容表
## 4. 分域与覆盖率表（分域必覆盖 + 总体 ≥50%）+ 工具真实操作流程表（三要素列；含无效触碰剔除、未覆盖域原因、`suspected_gaming` 依据）
## 5. GDA 工具表现评估（按选用的维度）
## 6. 问题记录（Q1、Q2…；类型 + 可复用性 + 五要素 + trace 引用 + 截图 + 因果三元组）
## 7. 优化建议（S1、S2…；按优先级，每条含实际收益、触发场景、验证方式、因果三元组）
## 8. 递归闭环产出（经验条目、优化提案、验证方式、下轮建议；软指标由独立子代理判定）
## 9. 通用事实 vs 本工程偶然现象 + 证据索引（截图、trace/log 路径、未覆盖项）
```

> digest 可解析约定：以上字段名与 Q/S 编号、`关卡数`、`机制清单`、`净可玩内容`、因果三元组、覆盖表三要素列、两行覆盖口径、`suspected_gaming` 均为固定写法，供 `bun run gda-dev-tools harness digest --round <轮目录>` 解析。`digest.json` 为只读派生品，不改写 `report.md` / `evidence.md`。分域覆盖、净可玩内容、跨 run 一致性若 digest 不解析，由独立子代理复核。

### 因果三元组格式（digest 可解析，第 2 / 6 / 7 / 8 节共用）

每环玩法增量、每条 Q、每条 S、每条经验条目各写一组因果三元组，按固定三段写在同一行：

```text
因果三元组：动作=<触发动作或工具调用>；条件=<复现条件或适用范围>；后果=<实际表现或影响>
```

三段缺任一视为不可解析，补写后再产出报告；只写本轮可观察证据，根因未定时「动作/条件」写「待分析」，不臆断。

### 玩法闭环验证表字段（第 3 节，硬验收）

逐项列出基线 → 改动后 → 证据；缺任一项不得声称完成。

| 玩法要素 | 基线 | 改动后 | 证据 |
| --- | --- | --- | --- |
| 主题契合 | | | `GAMEJAM.md` 约束在作品中的具体体现 |
| 核心玩法链（目标→挑战→反馈→结果） | | | |
| 胜利状态 | | | 状态读回 + 文本截图 |
| 失败状态 | | | 状态读回 + 文本截图 |
| 重玩与复位 | | | 复位前后读回值 |
| HUD 实时反馈 | | | 截图 |
| 视听反馈 | | | 已导入资源文件 + 节点引用读回 + 截图/日志；不接受内存态直接赋值 |
| 真实输入闭环 | | | `game_input` 注入 + 成对读回值 |
| 运行稳定性 | | | `get_game_log_entries` |

### 关卡机制与净可玩内容表（第 3 节附表，digest 可解析）

至少 3 关，关卡间须有**机制差异**（不是同一关改数字）。禁止用纯等待计时器凑时长；逐关写净可玩内容，不填估算。

| 关卡 | 主题/目标 | 本关核心机制 | 与上一关的机制差异 | 净可玩内容（去掉计时器后的最少有效操作与耗时） | 通关判据 | 证据 |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | | | — | | | |
| 2 | | | | | | |
| 3 | | | | | | |

表后写两行汇总：
`关卡数=<n>；机制数=<n>；关卡间有机制差异=是/否`。
`净可玩内容检验：每关有效操作时长占比≥50%=是/否；<列出占比最低的关卡及原因>`。

所有流程数据必须来自同一次连续 run，并在第 2 节标注 run 标识（起始时间戳 + trace_id）；跨 run 拼凑判 `suspected_gaming=true`。

### 分域与覆盖率表字段（第 4 节附表）

端到端测试须充分覆盖工具，分域必覆盖 + 总体 ≥50% 是硬门槛。按实际触达填写；不适用须写明理由（如主题为 2D 则 3D 域不适用）。

| 域 | 代表工具（触达的） | 状态（达标/缺失/不适用） | 证据 | 不适用理由 |
| --- | --- | --- | --- | --- |
| 场景与节点 | | | | |
| 资源与图像 | | | | |
| 音频 | | | | |
| 动画与 Tween | | | | |
| 2D 或 3D 核心 | | | | |
| 脚本 | | | | |
| 项目与输入配置 | | | | |
| 运行时与输入 | | | | |
| 捕获与日志 | | | | |
| 调试器与系统 | | | | |

图像与音频证据必须体现完整资源链路：生成内容 → 导出 `*.png`/`*.wav` 等文件 → `resource_import` 导入 → `resource_load` 读回 → 节点属性/脚本引用 `res://` 路径 → 运行截图/日志确认。仅有"内存态生成后直接赋值给节点"不计该域覆盖。

### 工具真实操作流程表字段（第 4 节）

每个工具一个真实操作流程，不是孤立试探；覆盖数以本轮真实轨迹与 252 canonical 名单 join 为准。前三列即反作弊三要素，必须同时填全；缺任一列判无效触碰并从覆盖中剔除。

| 工具 | 服务于哪个玩法功能 | 真实操作步骤 | 结果证据（读回值或截图） | 是否有效 |
| --- | --- | --- | --- | --- |
| | | | | 有效 / 无效触碰（注明缺失要素） |

表后单列三段：

- 无效触碰：`missing required parameter` 等调用，或三要素缺项者；列工具名、原因与缺失要素，不计有效覆盖。
- 未覆盖域与工具：列出缺失域及原因（模态工具需人工值守、仅特定场景适用等）；禁止为凑数盲调用补齐，但禁止把真实适用域标为不适用来逃避门槛。
- `suspected_gaming` 说明：证据与所声称玩法功能数不匹配、或跨 run 拼凑流程数据时写 `suspected_gaming=true` 并写明依据；该轮覆盖不进经验库，等待下一轮真实开发复核。表头口径行固定写：`覆盖 <N>/252，有效 <M>，无效触碰 <K>，达标=<是|否>，suspected_gaming=<是|否>（依据：...）`。

工程文档若写 `report/<ts>-report.md` 或 `report/img/`，以本技能路径为准，并在报告中说明覆盖。
