# 报告与问题条目模板

## 问题条目格式（SKILL.md §7 / report.md 第 6 节）

每条问题按五要素记录：触发场景、详细操作步骤、预期行为、实际表现（附证据）、问题分析（只基于本轮可观察证据；不读 GDA 源码补全根因，根因结论标记「待分析」）。格式：

```markdown
### Q1 [失败] <一句话标题>
- 触发场景：
- 操作步骤：
- 预期行为：
- 实际表现：
- 问题分析：
- 可复用性：通用 | 本工程
- trace：`<文件名>#seq=<n> | <tool> | ok=<bool> | error_code=<...> | duration_ms=<...> | request_id=<...>`
- 截图：`img/<文件名>`
- 因果三元组：动作=<...>；条件=<...>；后果=<...>
```

优化建议条目格式（SKILL.md §8 / report.md 第 7 节）：

```markdown
### S1 [优先级] <一句话标题>
- 实际收益：
- 触发场景：
- 验证方式：
- 因果三元组：动作=<...>；条件=<...>；后果=<...>
```

引擎崩溃类问题（SKILL.md §4.6）追加以下字段，其余条目不需要：

```markdown
- 崩溃归因：工具导致（写明可疑工具：`<tool>`）| 偶发 | 未定
- 可复现性：可复现（重试再次崩溃）| 不可复现 | 未尝试（附原因）
- 恢复次数：<n>；丢失增量：<描述或「无」>
```

## report.md 结构（第 8 节）

```markdown
# 端到端测试报告
- 开始时间 / 结束时间 / GDA 版本 / Godot 版本 / git HEAD / 主题 / 完成度
- 项目名 / 工程路径 / 主题 / 来源 / 抽样摘要 / draw_id（若本轮由 `jam e2e` 抽题；外部工程写「无」）
- 轨迹：`<集中根>/cli-traces/trace-YYYYMMDD.jsonl`（关键事件见 `evidence.md`）
- 日志：`<集中根>/projects/...`
- GOAL 终态：`active | paused | budgetLimited | usageLimited | complete | unmet`
- 关卡数：<n>；总通关时长：<分钟数>；冷启动无错：是 | 否
- 覆盖口径：`覆盖 <N>/252，有效 <M>，无效触碰 <K>，suspected_gaming=<是|否>（依据：...）`（由 `harness coverage` 的 `catalog_total=252` 口径统计；只读 `digest.json` 判定，不回写本报告）
- 因果三元组：动作 → 条件 → 后果（每环玩法增量一条，见第 2 节与第 8 节）

## 1. 结论摘要（含关卡数、总通关时长、GOAL 终态、覆盖口径行）
## 2. 执行过程（每环一段，随做随写；含每环三问答案与「动作→条件→后果」因果三元组）
## 3. 玩法闭环验证表（硬验收）+ 关卡与时长表
## 4. 工具真实操作流程表（三要素列；含无效触碰剔除、未覆盖原因、`suspected_gaming` 依据）
## 5. GDA 工具表现评估（按选用的维度）
## 6. 问题记录（Q1、Q2…；类型 + 可复用性 + 五要素 + trace 引用 + 截图 + 因果三元组）
## 7. 优化建议（S1、S2…；按优先级，每条含实际收益、触发场景、验证方式、因果三元组）
## 8. 递归闭环产出（经验条目、优化提案、验证方式、下轮建议；软指标由独立子代理判定）
## 9. 通用事实 vs 本工程偶然现象 + 证据索引（截图、trace/log 路径、未覆盖项）
```

> digest 可解析约定：以上字段名与 Q/S 编号、`关卡数`、`总通关时长`、因果三元组、覆盖表三要素列、`suspected_gaming` 均为固定写法，供 `bun run gda-dev-tools harness digest --round <轮目录>` 解析。`digest.json` 为只读派生品，不改写 `report.md` / `evidence.md`。

### 因果三元组格式（digest 可解析，第 2 / 6 / 7 / 8 节共用）

每环玩法增量、每条 Q、每条 S、每条经验条目各写一组因果三元组，按固定三段写在同一行：

```text
因果三元组：动作=<触发动作或工具调用>；条件=<复现条件或适用范围>；后果=<实际表现或影响>
```

三段缺任一视为不可解析，补写后再产出报告；只写本轮可观察证据，根因未定时「动作/条件」写「待分析」，不臆断。

### 玩法闭环验证表字段（第 3 节，硬验收）

逐项列出基线 → 改动后 → 证据；缺任一项不得声称完成。

| 玩法要素 | 基线 | 改动后 | 证据 |
| --- | --- | --- | --- |
| 主题契合 | | | `GAMEJAM.md` 约束在作品中的具体体现 |
| 核心玩法链（目标→挑战→反馈→结果） | | | |
| 胜利状态 | | | 状态读回 + 文本截图 |
| 失败状态 | | | 状态读回 + 文本截图 |
| 重玩与复位 | | | 复位前后读回值 |
| HUD 实时反馈 | | | 截图 |
| 视听反馈 | | | 脚本引用或截图 |
| 真实输入闭环 | | | `game_input` 注入 + 成对读回值 |
| 运行稳定性 | | | `get_game_log_entries` |

### 关卡与时长表（第 3 节附表，digest 可解析）

至少 3 关，完整通关流程不低于 5 分钟；逐关写实测值，不填估算。

| 关卡 | 主题/目标 | 通关判据 | 关卡通关时长 | 证据 |
| --- | --- | --- | --- | --- |
| 1 | | | | |
| 2 | | | | |
| 3 | | | | |

表后写一行汇总：`关卡数=<n>；总通关时长=<分钟数>；满足 ≥3 关且总通关 ≥5 分钟=是/否`。

### 工具真实操作流程表字段（第 4 节）

每个工具一个真实操作流程，不是孤立试探；覆盖数以 CLI 轨迹与 252 canonical 名单 join 为准，不设 KPI。前三列即反作弊三要素，必须同时填全；缺任一列判无效触碰并从覆盖中剔除。

| 工具 | 服务于哪个玩法功能 | 真实操作步骤 | 结果证据（读回值或截图） | 是否有效 |
| --- | --- | --- | --- | --- |
| | | | | 有效 / 无效触碰（注明缺失要素） |

表后单列三段：

- 无效触碰：`missing required parameter` 等调用，或三要素缺项者；列工具名、原因与缺失要素，不计有效覆盖。
- 未覆盖工具：列出工具名与原因（如模态工具需人工值守、仅特定场景适用），禁止为凑数盲调用补齐。
- `suspected_gaming` 说明：证据与所声称服务的玩法功能数不匹配时写 `suspected_gaming=true` 并写明依据；该轮覆盖不进经验库，等待下一轮真实开发复核。表头口径行固定写：`覆盖 <N>/252，有效 <M>，无效触碰 <K>，suspected_gaming=<是|否>（依据：...）`。

工程文档若写 `report/<ts>-report.md` 或 `report/img/`，以本技能路径为准，并在报告中说明覆盖。
