# 以充分测试工具为目标的端到端测试

端到端测试的首要目的是**测试工具的可靠性与覆盖面**：在真实完整开发流程中尽可能多地触达工具、发现缺陷。游戏是承载测试的载体，工具是被测对象。覆盖率是核心验收目标之一，不是副产品，也不能用「覆盖是自然结果」「不是 KPI」为不达标开脱。同时交付的游戏必须**可玩内容充分**：机制多样、关卡间有机制差异、有实时挑战，禁止用纯等待计时器把时长堆到某个数字。

## 本轮边界

- 报告侧唯一产物：`report/<YYYY-MM-DD_HH-MM>/` 下的 `report.md`、`evidence.md`、`img/`。
- 工程侧只允许修改 `examples/e2e`（或用户指定工程）与 `build/`、部署产生的 `addons/` 等构建产物。
- 不修改 `src/`、`devtools/`、`cli/`、`tests/`、`skills/`、`docs/wiki/`、`AGENTS.md`、`VERSION`、构建与测试配置。
- 不运行修复、不应用补丁、不提交 git。开工记录 `git status --porcelain` 基线，收尾比对，除被忽略目录外不得出现新的跟踪文件改动。
- 问题只记录现象、影响、复现步骤与证据；本轮不做根因分析与修复，疑似缺陷标「待分析」留给分析阶段。
- **执行期只读边界**：只读取 `<project-dir>/` 下的文档/素材/Godot 文件、本轮 `report/` 产物、GDA 工具返回的日志/轨迹/错误信息、`<project-dir>/.agents/skills/godot-autopilot-*`（仅查工具用法）。禁止读取 GDA 的 `src/`、`cli/`、`tests/`、`skills/`、`docs/wiki/`、`AGENTS.md` 与仓库根其他技能册；文件搜索限定在 `<project-dir>/` 与本轮报告目录内。
- 只执行 `bun run gda-dev-tools harness setup --project <project-dir>` 完成环境准备（必要时单独 `build` / `deploy`），读取命令输出，不读实现源码。

## 输入

- 识别工程标识：接受绝对路径、相对路径或 `examples/e2e` 写法。
- 收到工程路径时直接使用该工程，不重新抽题；若路径就是 `examples/e2e`，按新轮次先重置（用户明确要求续跑时除外）。
- 可接收本轮聚焦目标（如「重点验证脚本工具」），它调整验证侧重，但不降低分域必覆盖与总体 ≥50% 的门槛。
- 环境准备、前置探针、崩溃恢复与证据来源的操作细节见 `references/environment-protocol.md`（当准备环境、执行探针、处理崩溃或保存增量时读取）。

## 1. 校验输入

1. 规范化到绝对路径 `<project-dir>`。
2. 校验 `project.godot`；缺失时报错并停止。
3. 校验 `docs/` 与 `GAMEJAM.md`；两者缺失时请用户给出主题或先抽题，不降级为只读验收。存在 `GAMEJAM.md` 时按其主题推进，不因 `docs/` 缺失降级。

## 2. 读任务书

按顺序读取；后读文档不覆盖先读文档的硬约束：

1. `GAMEJAM.md`（存在时）：主题、抽样、创意约束、提交要求与评审维度，是本轮开发任务书。
2. `jam.json`（存在时）：主题、来源、抽样快照与工程元数据，用于报告溯源。
3. `docs/README.md`、`docs/test/test-plan.md`、`docs/test/acceptance.md`，以及 test-plan 阅读路径中相关的 `docs/gdd/`、`docs/tech/`、`docs/art/` 页面。
4. 若 `report/` 最近一轮存在 `analysis.md` 且对应本工程，只读取「待下一轮端到端验证项」作为附加观察点；缺失或无法确认时继续，不阻塞。

`GAMEJAM.md` 用于确定开发范围与主题；报告只评估 GDA 工具表现，不把游戏设计质量写成 `Q`。任务形态恒为开发型，工程已有内容时按主题补全而非只读验收。优先遵循工程文档约定；冲突时以工程文档为准并在报告中记录。只读查阅 `*.tscn`、`*.tres`、`project.godot` 用于核对与截图验证，不手动修改。

## 3. 前置检查

在仓库根执行固定 CLI 探针（`gda status`、`get_engine_state version`、`system_status` 连续两次）并读取基线：开始时间、`system_status.version`、引擎版本、`git rev-parse --short HEAD`、`git status --porcelain`；抽题轮记录主题、来源、`draw_id`、`jam.json` 抽样快照。探针命令、通过判据、退出码语义、失败恢复与环境准备步骤见 `references/environment-protocol.md`（当执行探针或准备环境时读取）。

## 4. 执行

### 4.1 可玩内容充分性（硬门槛，禁止计时器凑数）

在 §4.2 之前先确认作品满足以下全部条件，缺任一项不得声称完成：

- 主题契合：`GAMEJAM.md` 的创意约束在作品中有可指认体现。
- 核心玩法：至少一条「目标 → 实时挑战/失败 → 反馈 → 结果」链，挑战来自玩家操作或判断，不来自等待。
- 机制多样：至少 **3 种不同机制**，且关卡间有**机制差异**（不是同一关卡改数字）。例如空间移动、资源管理、物理平衡、时机反应、路径规划各算不同机制。
- 实时挑战：存在需要玩家在限定时间内持续决策或操作的压力；单纯「点一下然后等 100 秒」不算。
- 完整流程：开始 / 进行 / 胜利 / 失败 / 重玩复位，状态文本可见。
- 实时反馈：HUD 呈现关键状态，画面反馈（贴图/动画/Tween）与音频反馈均须存在；贴图与音频必须是**已导入的资源文件**并经正常资源引用播放/显示，不接受运行时内存生成直接赋值。
- 真实输入验证：经 `game_input` 注入完成完整循环，读回值与截图成对。
- 稳定性：运行期无引擎错误日志。

**净可玩内容检验（强制）**：记录「去掉计时器后的净可玩内容」——即在无限时条件下，玩家完成一关所需的最少有效操作与耗时。若某关 90% 以上时长是纯等待，该关判为不合格，必须用新机制替换等待，不得用加计时器满足时长。

### 4.2 六阶段开发流程

按「主题解读 → 玩法设计 → 场景与资源 → 脚本与配置 → 运行调试 → 闭环验证」推进。每阶段绑定工具类别与证据；**带 ★ 的工具类别属必覆盖域**，不得用 GDScript 内联逻辑绕过：

| 阶段 | 真实开发动作 | 必须使用的工具类别 | 产出证据 |
| --- | --- | --- | --- |
| 主题解读 | 读 `GAMEJAM.md` / `jam.json`，定主题与机制 | 文件读取 | 主题与机制摘记 |
| 玩法设计 | 定目标、挑战、机制差异、胜负、HUD、反馈 | 文件读取 | 玩法闭环验证表初稿 + 机制清单 |
| 场景与资源 | 场景骨架、★贴图/图像资源（代码生成→导出 `*.png`/`*.svg` →导入→引用）、★瓦片地图、动画资源 | `editor_scene_control`、`create_scene_node`、`property_set`、`texture_gen`/`image_edit`/`image_save`、`resource_import`/`resource_load`、`create_tilemap`/`create_tilemap_tileset`、`create_animation`/`create_animation_track` | 场景树读回、资源文件存在且被引用、编辑器截图 |
| 脚本与配置 | 玩法脚本、挂载、输入、★音频配置（代码生成→导出 `*.wav`/`*.ogg` →导入→引用）、★项目设置 | `create_script`、`patch_script`、`attach_script_to_node`、`set_input_map_action`、`os_file_write`/`resource_import`/`resource_load`、`audio_player`/`audio_bus`、`update_project_settings`/`get_project_settings` | 脚本 content_hash、音频资源文件存在且被引用、设置读回 |
| 运行调试 | 运行、输入、★Tween 动画、读回 | `game_input`、`game_tween`、`get_game_evidence`、`game_script` | 基线 vs 改动后读回值 + 动画截图 |
| 闭环验证 | 胜负、重玩、截图、稳定性 | `capture_editor_viewport`、`get_game_log_entries`、`game_scene_tree` | 完整循环截图 + 无错误日志 |

纪律：

1. 单环只做一个功能增量，不合并多个功能。
2. 每环开始前记录基线：同条件截图、读回值或日志。
3. 每环的「看」必须产生证据：结构类用编辑器截图，资源类用资源读回，运行类用游戏截图，逻辑类用读回值或日志。
4. 改动后用与基线相同条件复测，记录行为差异；不只写「通过」，必须给可比证据。
5. 每环结束回答三问：影响了哪个玩法指标？基线值与改动后值？若未影响玩法指标，说明为何值得做（如纯工具可靠性验证）。答案落入玩法闭环验证表。
6. 失败时区分「改动无效」与「引入回归」；回退引入回归的改动，只回滚本环。
7. 本环验收项全过才进入下一环；当场微调手感并复验，不带病进入下一环。
8. 存在本轮聚焦目标时优先覆盖该目标，同时交付可运行、可复验的增量。

### 4.3 工具覆盖：分域必覆盖 + 总体 ≥50%（核心验收）

覆盖统计口径、分域必覆盖表、图像音频生成例外、证据三要素与反作弊、未达标处理与报告固定口径行见 `references/coverage-protocol.md`（当统计覆盖、判定达标、处理反作弊或未达标时读取）。

### 4.4 保存、模态工具与崩溃恢复

保存优先与中毒兜底、模态工具受限、崩溃恢复与定位、证据来源表见 `references/environment-protocol.md`（当保存增量、调用模态工具或引擎崩溃时读取）。

### 4.5 长程机制

GOAL.md 字段与原子写、续跑规则、混合 verifier、无进展检测与恢复见 `references/goal-longrun.md`（当进行数小时多关开发、判定 verifier 或决定是否收尾时读取）。

## 5. 过程记录

1. 执行前创建本轮目录（见 §8）与其中 `report.md`，写标题、基本信息与「执行过程」标题。
2. 每环结束立即追加一段：环号、目标、基线证据、关键动作、改动后证据、行为差异、截图相对路径、本环新增覆盖工具与累计覆盖数、发现的问题。
3. 随做随写，不凭印象补写。流程数据只引用同一次连续 run，并标注 run 标识。
4. 不抄录全量调用序列；只摘录支撑结论的关键事件（工具名、参数摘要、ok、error_code、duration_ms、request_id）。
5. 每环结束按原子写同步更新 GOAL.md 的 `checkpoints` 与 `state`。

## 6. 证据

证据来源、脱敏口径、`evidence.md` 摘录规则与路径占位写法见 `references/environment-protocol.md`（当采集或引用证据时读取）。

## 7. 评估

从资深使用者与开发者视角评估 GDA，记录不足与良好表现；不找茬、不夸大。把影响推进的负面表现登记为第 6 节带编号问题条目；第 5 节只做归纳，不留无法追溯的结论。

登记门槛：只登记影响真实推进、可复现的问题；有简单绕过且不影响结果的不登记；问题数量不是 KPI。按以下维度选用，无发现跳过、不凑数：

工具完备性、参数与数据合理性、日志、步骤合并/快捷工具、错误处理与恢复、性能与效率、一致性与幂等性、可发现性与文档、可组合性与工作流、上下文感知与状态管理、安全与权限、兼容性与版本适配、可测试性与验证、可视化与反馈、资源/场景/脚本操作覆盖、任务规划与自主性、与 Godot 原生工作流对比、工具粒度与依赖、返回值结构化与机器可读。

问题条目按本轮唯一连续的 `Q<n>` 编号，类型=失败/缺陷/体验/文档、可复用性=通用/本工程，按五要素记录，根因标「待分析」。引擎崩溃按 `references/environment-protocol.md` 追加归因、可复现性、恢复次数与丢失增量。编号规则与格式见 `references/report-templates.md`「问题条目格式」。

## 8. 报告

- 本轮目录 `report/<YYYY-MM-DD_HH-MM>/`，取本地开始时间；已存在追加 `-2`、`-3`，不覆盖。写 `report.md`、`img/`、`evidence.md`；不创建或改写 `analysis.md`；本轮结束后不再改写这些文件。
- 报告必须含「玩法闭环验证表」「分域与覆盖率表」「工具真实操作流程表」三节（字段见模板），缺任一不得声称完成。
- 报告头部与第 4 节必须写覆盖口径行与分域覆盖行（固定写法见 `references/coverage-protocol.md`「报告固定口径行」）。
- 报告必须记录关卡数、机制清单、净可玩内容、GOAL 终态、Q/S 条目、因果三元组与 `suspected_gaming` 结论（字段见模板），供 `harness digest --round <轮目录>` 解析；digest 不解析项由独立子代理复核。
- `digest.json` 只读，不回写报告或 `evidence.md`。`harness coverage` 的 `round_start_ms` 已知可能错误，报告以本轮轨迹真实起始时间过滤为准并说明差异。
- 优化建议：`S1`、`S2`… 按优先级（阻塞开发 > 显著降低效率 > 影响结果正确性 > 提升长期可维护性），只写实际遇到且影响推进、能说明收益/触发场景/验证方式、非过度设计的建议。结构见 `references/report-templates.md`。

`report.md` 结构、Q/S 与因果三元组格式、三张硬验收表字段见 `references/report-templates.md`（当编写报告或填写问题/建议条目时读取）。

## 9. 递归优化闭环

本轮只执行「在线探索」与「证据沉淀」；「离线评估」与「部署改进」留给后续轮次，执行前取得用户明确授权。

- 用真实开发动作、轨迹与报告完成在线探索与证据沉淀。
- 把 `report/` 下所有轮目录作为证据池，跨轮累积；每轮自包含报告、截图、关键事件摘录、对照证据与后续 `analysis.md`（若存在）；不新建索引文件。
- 每轮新增一条可回放记录：本轮 `report.md`、`evidence.md`、关键对照（Q 编号与基线/改动后差异）、`analysis.md`（若存在）。历史证据不足时由分析阶段用最小复现代替回放，并在报告注明。
- 报告第 9 节区分：GDA 通用事实（换工程仍成立，写明复现条件）与本工程偶然现象（仅本工程/本次会话，写明未跨工程验证）。

## 10. 禁止事项

- 禁止绕过 GDA 手动编辑任何 Godot 工程文件（`*.tscn`、`*.tres`、`*.gd`、`project.godot` 等）。
- 禁止无记录重启 Godot；任何重启先按 `references/environment-protocol.md` 记录上下文再自重启。
- 禁止更新 `docs/wiki/`、`AGENTS.md` 或技能文件；禁止修改 GDA 源码、构建或测试配置。
- 禁止在本轮修复工具问题、应用补丁或运行修改命令；修复留分析会话。
- 禁止编造、夸大或凭印象补写工具表现与调用记录；禁止跨 run 拼凑流程数据，所有流程数据来自同一次连续 run。
- 禁止用「GDScript 一把梭」绕过资源、图像、音频、动画、瓦片、项目设置等真实开发必用工具（工具确实不支持时须在报告注明）；禁止把图像/音频以内存态直接赋值给节点属性；禁止在 2D 游戏硬调 3D 工具等无开发意图的盲调用凑数。
- 禁止把「覆盖是自然结果」「不是 KPI」当作覆盖不达标的借口；禁止用纯等待计时器把时长堆到指标。
- 禁止为凑评估维度硬评，禁止把理论上的「最好有」写成优化建议。
- 禁止无人值守会话调用 `show_display_dialog`、`open_os_path` 及未确认保护的模态弹窗工具。
- 禁止提交 git。

## 11. 终止与收尾

出现以下情况立即停止并转报告：GDA 致命缺陷无法继续开发；Godot 崩溃按 `references/environment-protocol.md` 无法恢复（同一崩溃 3 次未定位或工程无法还原）；前置检查失败且无法在不违反约束下恢复；覆盖门槛经 `references/coverage-protocol.md` 补做仍不达标（记 `unmet`）。

收尾前逐项核对：

- 轮目录名 `YYYY-MM-DD_HH-MM`（零填充），按目录名可排序取最新；含 `report.md`、`img/`、`evidence.md`，截图引用均为相对路径。
- 报告 9 节齐全，含「玩法闭环验证表」「分域与覆盖率表」「工具真实操作流程表」，问题均有证据。
- 作品满足 §4.1 全部条件，净可玩内容检验通过，或明确列出未达标项；图像与音频资源均为已导入的 `res://` 资源文件并经引用生效，非内存态直接赋值。
- 分域必覆盖达标、总体有效覆盖 ≥50%；每个计入覆盖工具三要素齐全，无效触碰已剔除，未覆盖域已说明不适用理由；两行固定口径与 `suspected_gaming` 依据已写入。
