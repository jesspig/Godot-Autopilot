# GDA Game Jam

用 GDA 把 Game Jam 主题做成完整、可运行、可提交的游戏。游戏质量、创意与交付完整度是唯一目标；工具问题只作为阻塞处理。

## 目标与边界

- 目标：交付一款有明确钩子、核心循环可玩、视听完整、能现场运行的游戏。
- 目标：按 `GAMEJAM.md` 的提交要求准备作品说明，作品能直接用于比赛提交。
- 边界：不修改 GDA 源码、`devtools/`、`cli/`、`tests/`、`docs/wiki/`、`AGENTS.md`、`VERSION`。
- 边界：不修改用户固定维护的 `devtools/templates/gamejam/brief.md`。

## 输入

- 未给主题：从题库随机抽题。
- 给了主题：使用该主题；`--theme` 先匹配 `id`，再匹配唯一的展示名。
- 给了概念、项目名或范围：优先采用；未给时自行构思。
- 给了工程路径：在该工程继续开发；存在 `GAMEJAM.md` 时按它推进，不存在时按用户要求推进。
- 模板是唯一提交要求来源；本技能不额外增加必填文档或结构。

## 1. 抽题与读题

1. 在仓库根执行 `bun run gda-dev-tools jam --json`；需要指定主题时加 `--theme <id|主题名>`。
2. 记录 `theme_id`、`theme`、`source`、`intake_path`、`draw_id`。
3. 读取 `intake_path/GAMEJAM.md` 与 `intake_path/jam.json`；提取主题、抽样关键词、概念灵感、创意约束、提交要求与评审维度。
4. 确认 intake 只用于读题；不要在 intake 中开发、部署或打开 Godot。
5. 一轮只抽一次题；不要在开发中途换主题或重新抽题。
6. 开发中遵守 `GAMEJAM.md` 的「创意约束」；它与模板建议冲突时，以创意约束为准。

## 2. 概念与范围

1. 从抽样关键词与概念中生成 3–5 个方向；组合、反转、极端化或落到具体场景，选最有钩子的一个。
2. 用一句话写清 pitch：玩家是谁、做什么、为什么有趣。
3. 定核心循环：输入 → 反馈 → 奖励/惩罚 → 下一轮；写清操作方式与一轮可玩内容。
4. 定主题诠释：机制、叙事或表现至少有一层与主题直接对应，避免只在标题上贴主题。
5. 定记忆点：玩家离开后最容易记住的一个机制、画面或声音。
6. 定范围上限：一个核心机制、一个可玩循环、5–10 分钟内容；先保证完整，再考虑扩展。
7. 长轮次或需要跨会话恢复时，可在项目根维护 `DEVLOG.md`，只记决策、阻塞与下一步；默认不建。

## 3. 命名与创建

1. 基于概念构思 2–3 个项目名；选定展示名与 ASCII slug。
2. 在仓库根执行：

   ```bash
   bun run gda-dev-tools jam create --theme <theme_id> --name "<项目名>" --slug "<slug>" --json
   ```

3. 读取返回的 `path` 作为 `<project-dir>`；确认只包含 `project.godot`、`GAMEJAM.md`、`jam.json` 三个骨架文件。
4. 不手工创建最终项目目录，不手工拼 `<slug>-<hash8>`。
5. 创建失败时停止并报告；不得在 intake 中继续开发。

## 4. 安装插件与打开工程

1. 创建成功后立即执行：

   ```bash
   bun run gda-dev-tools build
   bun run gda-dev-tools deploy --project <project-dir>
   ```

2. 请用户在 Godot 编辑器中打开 `<project-dir>` 并启用插件；不自行启动或重启 Godot。
3. 在仓库根执行只读探针：

   ```bash
   gda status --project <project-dir> --json
   gda call --project <project-dir> get_engine_version
   gda call --project <project-dir> system_status
   ```

4. `gda status` 的 `project` 必须与 `<project-dir>` 一致；编辑器仍打开其他工程时，请用户切换或重新打开。
5. `system_status` 必须返回 `running=true`；不可达时停止，说明需要打开工程并启用插件。
6. 记录基线：开始时间、GDA 版本、Godot 版本、`git rev-parse --short HEAD`、主题与 `draw_id`。

## 5. 垂直切片

1. 先做最小可玩闭环：场景、脚本、输入、反馈、胜负/结束条件。
2. 只经 GDA 创建和修改工程文件；`jam create` 生成的骨架除外，生成后不得再手改。
3. 优先把“一句话 pitch + 核心循环”跑通；占位美术、临时音效可以后补。
4. 冷启动运行一次：从工程根启动，确认没有阻断性错误。
5. 垂直切片可玩前，不扩展关卡、菜单或内容量。

## 6. 创意迭代

1. 每轮只做一个功能增量；每轮结束实际运行并试玩。
2. 用 GDA 留证：游戏截图、读回值、输入注入结果、日志或错误流。
3. 试玩后只回答一个问题：这一轮让核心乐趣变强还是变弱？
4. 变强则加码；变弱则回退本环，不带着问题进入下一轮。
5. 优先打磨钩子与核心反馈，其次才是内容量、难度曲线与外围系统。
6. 玩法、手感、难度与节奏的微调当场复验；不把明显不舒服的状态留到收尾。

## 7. 表现与音频

1. 保证画面可辨：玩家、威胁、目标、可交互物在截图里能一眼区分。
2. 加操作提示与必要 HUD；菜单、暂停、重开与结束状态都要能走通。
3. 至少加入一条音乐循环与关键动作音效；音频是独立评审项，不能完全缺失。
4. 用截图检查视觉一致性；用音频节点、播放状态或日志确认声音确实触发。
5. 需要画面特效时优先用 Godot 原生节点与内置资源，避免引入来源不明的素材。
6. 素材来源与许可写入作品说明；不使用无法说明来源的素材。

## 8. 内容与收尾

1. 内容量服从范围上限：优先一个完整循环，而不是多个半成品。
2. 检查失败/结束条件、重开流程、暂停与退出；确保玩家不会卡死。
3. 检查难度曲线：第一分钟能上手，后续有变化，不出现无法通过或无聊等待。
4. 从工程根冷启动一次，确认没有缺失资源、脚本错误或插件依赖问题。
5. 记录运行方式、操作说明、依赖与特殊输入设备；需要网络或外部服务时一并说明。

## 9. 作品说明

1. 按 `GAMEJAM.md` 的提交要求准备作品说明；默认文件名为 `SUBMISSION.md`，用户指定其他格式时按用户。
2. 内容覆盖模板建议的维度：概念设计、灵感来源、创作思路、核心玩法与机制、关卡或流程、美术与音频方向、主题诠释、操作说明、团队分工（如适用）、素材许可（如适用）。
3. 不新增模板之外的必填章节；模板没有要求的内容可以作为可选补充。
4. 作品说明与工程实现保持一致；不写未实现的功能。
5. 需要时把 `SUBMISSION.md` 放在项目根，确保提交时能随工程一起取用。

## 10. 交付验收

1. 按固定模板的六项评审维度自检，并准备证据：

   | 维度 | 自检问题 | 证据 |
   |---|---|---|
   | Overall | 能运行、能完整玩一轮吗？ | 冷启动截图、运行状态 |
   | Gameplay | 核心循环有趣、输入反馈清楚吗？ | 试玩截图、输入注入结果 |
   | Graphics | 画面可辨、风格一致吗？ | 游戏截图 |
   | Audio | 有音乐与关键音效吗？ | 音频节点、播放证据 |
   | Innovation | 钩子或机制有新意吗？ | 机制说明、实现证据 |
   | Theme Interpretation | 主题落到机制或叙事了吗？ | 机制与主题对应说明 |

2. 收尾执行 `bun run gda-dev-tools jam index`，把项目登记进 `examples/INDEX.md`。
3. 最终交付说明写清：项目名、主题、赛事与来源、工程路径、运行方式、操作、已覆盖内容、已知缺口。
4. 自动试玩不能替代人工试玩；最终把需要用户亲自体验的部分明确列出。

## 11. 工具问题处理

- 小问题：换参数、换等价工具、换实现路径，直接绕过。
- 影响推进但可绕过：记一句在 `DEVLOG.md` 或最终交付说明里，继续做游戏。
- 无法绕过且阻塞交付：停止，说明阻塞点、复现步骤与已尝试的替代路径，等待用户决定。
- 不读 GDA 源码定位根因；不修改工具、文档、技能或测试。
- 不把工具问题写进作品说明或评审自检；它们不是游戏内容。

## 12. 禁止事项

- 禁止在 intake（`examples/<主题>/project/`）中开发、部署或打开 Godot。
- 禁止手工创建最终项目目录或手工拼 `<slug>-<hash8>`；必须使用 `jam create`。
- 禁止在开发过程中再次调用 `jam` 或 `jam create`，禁止切换主题；一轮只抽一次题、只创建一个项目。
- 禁止使用 `jam e2e`；比赛项目只走 `jam create`。
- 禁止绕过 GDA 手动编辑 Godot 工程文件（`*.tscn`、`*.tres`、`*.gd`、`project.godot` 等）；`jam create` 生成的骨架除外。
- 禁止修改 `devtools/templates/gamejam/brief.md`、GDA 源码、`devtools/`、`cli/`、`tests/`、`docs/wiki/`、`AGENTS.md`、`VERSION`。
- 禁止主动重启 Godot；引擎崩溃时停止并如实记录。
- 禁止编造、夸大或凭印象补写试玩结果与证据。
- 禁止提交 git、推送、打 tag 或升版。

## 13. 交付清单

- 游戏能从工程根冷启动，核心循环可完整走通。
- 操作说明、胜负/结束、重开与暂停可用。
- 画面可辨，至少有音乐与关键音效。
- 主题诠释能落到机制、叙事或表现。
- `SUBMISSION.md` 按 `GAMEJAM.md` 要求完成，内容与实现一致。
- `examples/INDEX.md` 已包含本项目。
- 已知缺口、未验证项与需要人工试玩的部分已明确说明。
- 本轮未修改 GDA 源码、文档、技能或固定模板。
