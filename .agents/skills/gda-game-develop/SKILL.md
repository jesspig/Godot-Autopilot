# GDA 究极游戏开发

用 GDA 围绕主题自主创作并交付一款**究极完善、足以拿奖、可直接上架**的游戏。目标是六维评分（Overall / Gameplay / Graphics / Audio / Innovation / Theme Interpretation）全部达到冠军水准，而非仅可运行或可提交。美术与音频素材全部自主创作，不依赖来源不明或外部素材。支持数小时长程任务：开工先写 `GOAL.md`，按关连续推进、逐关留证与存检查点，不中途打扰用户（见 §14）。

## 目标与验收标准

- **总目标**：交付一款钩子鲜明、核心循环扎实、视听完整、关卡丰富、能现场运行且可直接上架的游戏，并按 `GAMEJAM.md` 准备可直接提交的作品说明；长程任务推进到 `GOAL.md` 的 `complete` 或 `unmet`，全程留下可被离线回放消费的结构化自检证据（§14、§15）。
- **六维夺冠标准**（每维均须给出通过证据，任一维不达标不得声称完成）：
  - Overall：冷启动无阻断错误，能完整走通一轮，整体完成度达到可上架水准。
  - Gameplay：核心循环有趣、输入反馈清楚、机制多样、难度曲线合理。
  - Graphics：画面可辨、美术风格统一且由本项目自主创作，无占位、无来源不明素材。
  - Audio：有音乐循环与关键动作音效，均由本项目自主创作并经资源链路接入。
  - Innovation：钩子或机制有新意，不是常见玩法的换皮。
  - Theme Interpretation：主题落到机制、叙事或表现，而非只在标题贴主题。
- **边界**：只改比赛工程本身，不改 GDA 源码、工程模板与常驻文档（详见 §12）。

## 输入

- 未给主题：从题库随机抽题。
- 给了主题：使用该主题；`--theme` 先匹配 `id`，再匹配唯一的展示名。
- 给了概念、项目名或范围：优先采用；未给时自行构思。
- 给了工程路径：在该工程继续开发；存在 `GAMEJAM.md` 时按它推进，不存在时按用户要求推进。
- 模板是唯一提交要求来源；本技能不额外增加必填文档或结构。

## 1. 抽题与读题

1. 在仓库根执行 `bun run gda-dev-tools jam --json`；需要指定主题时加 `--theme <id|主题名>`。
2. 记录 `theme_id`、`theme`、`source`、`intake_path`、`draw_id`。
3. 读取 `intake_path/GAMEJAM.md` 与 `intake_path/jam.json`；提取主题、抽样关键词、概念灵感、创意约束、提交要求与评审维度。
4. 确认 intake 只用于读题；不要在 intake 中开发、部署或打开 Godot。
5. 一轮只抽一次题；不要在开发中途换主题或重新抽题。
6. 开发中遵守 `GAMEJAM.md` 的「创意约束」；它与模板建议冲突时，以创意约束为准。

## 2. 概念与范围

1. 从抽样关键词与概念中生成 3–5 个方向；组合、反转、极端化或落到具体场景，选最有钩子、最有创新潜力的一个。
2. 用一句话写清 pitch：玩家是谁、做什么、为什么有趣。
3. 定核心循环：输入 → 反馈 → 奖励/惩罚 → 下一轮；写清操作方式与一轮可玩内容。
4. 定主题诠释：机制、叙事或表现至少有一层与主题直接对应，避免只在标题上贴主题。
5. 定记忆点与创新点：玩家离开后最容易记住的一个机制、画面或声音；明确它相对常见玩法的差异。
6. 定范围：至少 3 个可游玩关卡，关卡间有机制差异，完整通关流程不低于 5 分钟；先跑通核心闭环，再按关卡计划扩展全部内容，不交付占位或半成品。
7. 长轮次或需要跨会话恢复时，先按 §14 在项目根写入 `GOAL.md`，再按需维护 `DEVLOG.md`（只记决策、阻塞与下一步）；`DEVLOG.md` 默认不建，`GOAL.md` 为长程必建。

## 3. 命名与创建

1. 基于概念构思 2–3 个项目名；选定展示名与 ASCII slug。
2. 在仓库根执行：

   ```bash
   bun run gda-dev-tools jam create --theme <theme_id> --name "<项目名>" --slug "<slug>" --json
   ```

3. 读取返回的 `path` 作为 `<project-dir>`；确认只包含 `project.godot`、`GAMEJAM.md`、`jam.json` 三个骨架文件。
4. 不手工创建最终项目目录，不手工拼 `<slug>-<hash8>`。
5. 创建失败时停止并报告；不得在 intake 中继续开发。

## 4. 引擎准备与基线

1. 创建成功后立即执行一条命令完成装插件与启动引擎：

   ```bash
   bun run gda-dev-tools harness setup --project <project-dir>
   ```

   该命令按序完成构建、部署、启动引擎、列出工程、核对状态与连通性；默认启动完整 Godot 编辑器，无显示环境才用 headless 回退。全程自行完成，不把启动或启用插件交回用户。

2. 引擎由本流程自主启动；若崩溃，先按 §14.4 记录上下文（最后一个调用、日志尾部、未保存增量）再自主重启恢复，不中途要求用户介入。

3. 在仓库根执行只读探针复核工程与运行状态：

   ```bash
   gda status --project <project-dir> --json
   gda call --project <project-dir> get_engine_version
   gda call --project <project-dir> system_status
   ```

4. `gda status` 的 `project` 必须与 `<project-dir>` 一致；不一致时按 §14.4 记录后自主重启引擎并重连，不请用户切换工程。
5. `system_status` 必须返回 `running=true`；不可达时按 §14.4 归因与重启恢复，仍不可达则停止并报告阻塞点。
6. 记录基线：开始时间、GDA 版本、Godot 版本、`git rev-parse --short HEAD`、主题与 `draw_id`；把引擎启动与恢复情况登记到 `GOAL.md` 的 `blocker` / `checkpoints`（按 §14）。

## 5. 垂直切片

1. 先做最小可玩闭环：场景、脚本、输入、反馈、胜负/结束条件。
2. 只经 GDA 创建和修改工程文件；`jam create` 生成的骨架除外，生成后不得再手改。
3. 优先把「一句话 pitch + 核心循环」跑通；占位美术、临时音效可以后补，但必须在收尾前替换为自主创作的正式素材。
4. 冷启动运行一次：从工程根启动，确认没有阻断性错误。
5. 垂直切片可玩前，不扩展关卡、菜单或内容量。

## 6. 创意迭代

1. 每轮只做一个功能增量；每轮结束实际运行并试玩。
2. 用 GDA 留证：游戏截图、读回值、输入注入结果、日志或错误流。
3. 试玩后只回答一个问题：这一轮让核心乐趣变强还是变弱？
4. 变强则加码；变弱则回退本环，不带着问题进入下一轮。
5. 优先打磨钩子与核心反馈，其次才是内容量、难度曲线与外围系统。
6. 玩法、手感、难度与节奏的微调当场复验；不把明显不舒服的状态留到收尾。

## 7. 自主创作美术与音频素材

素材全部自主创作，达到统一风格与可上架水准；不使用来源不明素材，不把占位资源留到交付。所有素材经工具生成后必须落盘为资源文件（`*.png` / `*.svg` / `*.wav` / `*.ogg` 等）并经正常导入与引用链路接入，禁止内存态直接赋值。

### 7.1 美术素材

1. 先定美术风格（配色、形状语言、像素/矢量/手绘质感、UI 风格），贯穿全部画面，保证 Graphics 维度风格一致。
2. 用 `texture_gen`、`image_edit`、`image_pixel` 等工具生成角色、场景、道具、背景、图标、UI 元素与特效贴图；需要程序化图案时用噪声、渐变、径向填充等能力。
3. 用 `image_save` 落盘为 `res://` 下的资源文件；通过 `resource_import` 导入、`resource_load` 读回，并在场景属性或脚本中以 `res://` 路径引用。
4. 用 `create_tilemap_tileset` / `set_tileset_source` 组织瓦片资源，为 2D 场景构建地形与关卡。
5. 用 `create_animation` / `create_animation_track` 制作角色与场景动画；用 Godot 原生节点与内置资源实现特效，不引入外部素材。
6. 逐项读回验证：资源文件存在、节点属性指向 `res://` 路径、截图确认画面一致且无占位。

### 7.2 音频素材

1. 用代码或工具生成 PCM 采样内容，落盘为 `*.wav` / `*.ogg` 资源文件（如 `os_file_write` 写文件后 `resource_import` 导入）；禁止运行时生成后直接赋值给节点属性。
2. 至少一条与主题氛围匹配的音乐循环，以及关键动作音效（跳跃、得分、受伤、胜利、失败等）；音频是独立评审项，不能完全缺失。
3. 用 `audio_player`、`audio_bus` 播放并控制音量/音调；通过播放状态或日志确认声音确实触发。
4. 逐项读回验证：资源文件存在、节点/播放器引用 `res://` 路径、运行日志或播放状态确认生效。
5. 素材的来源与许可在作品说明中标注为本项目自主生成（§9）。

## 8. 内容与收尾

1. 内容量服从范围上限：优先把每个关卡做完整、做出机制差异，而不是多个半成品。
2. 检查失败/结束条件、重开流程、暂停与退出；确保玩家不会卡死。
3. 检查难度曲线：第一分钟能上手，后续有变化，不出现无法通过或无聊等待。
4. 从工程根冷启动一次，确认没有缺失资源、脚本错误或插件依赖问题。
5. 记录运行方式、操作说明、依赖与特殊输入设备；需要网络或外部服务时一并说明。

## 9. 作品说明

1. 按 `GAMEJAM.md` 的提交要求准备作品说明；默认文件名为 `SUBMISSION.md`，用户指定其他格式时按用户。
2. 内容覆盖模板建议的维度：概念设计、灵感来源、创作思路、核心玩法与机制、关卡或流程、美术与音频方向、主题诠释、操作说明、团队分工（如适用）、素材许可（如适用）。
3. 素材许可一栏写明美术与音频均为本项目用 GDA 工具自主生成，不引入外部素材；若确有外部素材，写明来源与许可。
4. 不新增模板之外的必填章节；模板没有要求的内容可以作为可选补充。
5. 作品说明与工程实现保持一致；不写未实现的功能。
6. 需要时把 `SUBMISSION.md` 放在项目根，确保提交时能随工程一起取用。

## 10. 交付验收

1. 按六项评审维度逐维自检并准备证据，每维须达到冠军水准；任一维仅「可运行」或「缺失」不得声称完成：

   | 维度 | 自检问题（夺冠标准） | 证据 |
   |---|---|---|
   | Overall | 冷启动无错、完整流程可走通、完成度达到可上架吗？ | 冷启动截图、运行状态、完整流程截图 |
   | Gameplay | 核心循环有趣、机制多样、反馈清楚、难度曲线合理吗？ | 试玩截图、输入注入结果、机制清单 |
   | Graphics | 画面可辨、美术自主创作、风格统一、无占位吗？ | 游戏截图、资源文件与引用读回 |
   | Audio | 有自主创作的音乐循环与关键音效并经资源链路接入吗？ | 音频资源文件、播放状态或日志 |
   | Innovation | 钩子或机制相对常见玩法有新意吗？ | 机制说明、实现证据、与常见玩法的差异 |
   | Theme Interpretation | 主题落到机制、叙事或表现而非仅贴标题吗？ | 机制与主题对应说明、实现证据 |

   > 本表六维自检的结论与证据引用同时按 §15 写入结构化自检证据，随每关/每轮交付保存，供离线回放按证据查阅。

2. 收尾执行 `bun run gda-dev-tools jam index`，把项目登记进 `examples/INDEX.md`。
3. 最终交付说明写清：项目名、主题、赛事与来源、工程路径、运行方式、操作、已覆盖内容、已知缺口。
4. 自动试玩不能替代人工试玩；最终把需要用户亲自体验的部分明确列出。

## 11. 工具问题处理

- 小问题：换参数、换等价工具、换实现路径，直接绕过。
- 影响推进但可绕过：记一句在 `DEVLOG.md` 或最终交付说明里，继续做游戏。
- 无法绕过且阻塞交付：停止，说明阻塞点、复现步骤与已尝试的替代路径，等待用户决定。
- 不读 GDA 源码定位根因；不修改工具、文档、技能或测试。
- 不把工具问题写进作品说明或评审自检；它们不是游戏内容。

## 12. 禁止事项

- 禁止在 intake（`examples/<主题>/project/`）中开发、部署或打开 Godot。
- 禁止手工创建最终项目目录或手工拼 `<slug>-<hash8>`；必须使用 `jam create`。
- 禁止在开发过程中再次调用 `jam` 或 `jam create`，禁止切换主题；一轮只抽一次题、只创建一个项目。
- 禁止使用 `jam e2e`；比赛项目只走 `jam create`。
- 禁止绕过 GDA 手动编辑 Godot 工程文件（`*.tscn`、`*.tres`、`*.gd`、`project.godot` 等）；`jam create` 生成的骨架除外。
- 禁止修改 `devtools/templates/gamejam/brief.md`、GDA 源码、`devtools/`、`cli/`、`tests/`、`docs/wiki/`、`AGENTS.md`、`VERSION`。
- 禁止未记录上下文就重启 Godot；崩溃时先记录最后一个调用、日志尾部与未保存增量，再按 §14.4 自主重启恢复，不把未经记录的重启带进交付。
- 禁止使用来源不明、无法说明许可的外部美术或音频素材；禁止把占位素材或运行时内存态素材留到交付（§7）。
- 禁止编造、夸大或凭印象补写试玩结果与证据。
- 禁止提交 git、推送、打 tag 或升版。

## 13. 交付清单

- 游戏能从工程根冷启动，核心循环可完整走通，完成度达到可上架水准。
- 操作说明、胜负/结束、重开与暂停可用。
- 至少 3 关且关卡间有机制差异，完整通关流程不低于 5 分钟。
- 六维评分全部达到冠军水准并有证据；任一维不达标不得声称完成（§10）。
- 美术与音频素材均为本项目自主创作，已落盘为资源文件并经正常导入与引用链路接入，无占位、无来源不明素材（§7）。
- `SUBMISSION.md` 按 `GAMEJAM.md` 要求完成，内容与实现一致，素材许可标注为自主生成。
- `examples/INDEX.md` 已包含本项目。
- 已知缺口、未验证项与需要人工试玩的部分已明确说明。
- 长程任务的 `GOAL.md` 已推进到 `complete` 或 `unmet`，每关/每轮结构化自检证据已保存（§14、§15）。
- 本轮未修改 GDA 源码、文档、技能或固定模板。

## 14. 长程任务与 GOAL.md

面向数小时、至少 3 关、完整通关流程不低于 5 分钟的长程任务。开工先写 `GOAL.md`，全程按它连续推进。

### 14.1 GOAL.md 字段与原子写

- 位置：项目根 `GOAL.md`，为运行时产物；开工时先写入初版，规则本身不预建其他结构。
- 字段：
  - `objective`：一句话总目标（做出什么游戏、达到什么交付状态）。
  - `acceptance`：可判定的验收条件，至少含关卡 ≥ 3、完整通关流程 ≥ 5 分钟、关卡间机制差异、六维自检全部达到冠军水准且证据齐全、美术与音频素材均为自主创作并接入、冷启动无阻断性错误。
  - `limits`：预算 / 时间 / 范围上限，作为自动推进的停止边界。
  - `state`：取值仅限 `active`、`paused`、`budgetLimited`、`usageLimited`、`complete`、`unmet`。
  - `completionEvidence`：指向完成证据的路径或引用（关卡状态、六维自检结论、素材资源与引用读回、冷启动 / 重开 / 暂停状态、DEVLOG 决策点）。
  - `blocker`：当前阻塞点，无阻塞写「无」。
  - `checkpoints`：按关 / 按轮的检查点列表，每项含关卡或轮次标识、状态、证据引用、时间戳。
- 原子写：任何字段更新都先写临时文件再重命名覆盖 `GOAL.md`，不原地多次写入；写入失败保留上一版，不产生半截状态。

### 14.2 continuation rule（连续推进）

1. 每关或每轮完成后按顺序执行：保存工程 → 由 verifier 判定（§14.3）→ 写 checkpoint（含证据引用）→ 更新 `GOAL.md` 字段。
2. 判定未通过且未触达 `limits` 时，自动进入下一关或下一轮，禁止提前收尾。
3. 仅在以下情况通知用户：`state` 为 `complete` 或 `unmet`、出现 `blocker`、`active` 之外且触达 `limits`（`budgetLimited` / `usageLimited`）；其余过程不中断用户。
4. 触达 `limits` 后停止自动推进，写清未达成项，并把 `state` 置为对应的受限值。

### 14.3 混合 verifier

- 硬指标（关卡数、机制差异、完整通关时长、素材资源存在与引用、六维证据是否齐全、冷启动与重开 / 暂停运行状态）按已保存证据判定，不靠开发者口述。
- 软指标（创意、手感、主题诠释、画面表现、音频品质）由独立子代理判定；开发者不对自己的作品做软指标自评。
- verifier 结论写入 checkpoint 与 `GOAL.md` 的 `completionEvidence`，只记录判定结果与证据引用，不在此改编判定逻辑。

### 14.4 无进展检测与恢复

- 连续 2 次关卡或轮次没有玩法或内容进展（无新可玩内容、无机制 / 视听增量）→ 把 `state` 置为 `paused`，写明阻塞与已尝试路径，并按 §14.2 报告。
- 恢复时读取 `GOAL.md` 末态 + 已保存证据 + 当前工程状态，从最后一个 checkpoint 续跑；`complete` 与 `unmet` 不续跑。
- 引擎崩溃按 §4.2 先记录上下文再自主重启；恢复后先用 §4.3 探针核对工程与运行状态，再继续下一段，每次恢复记入 checkpoints。

## 15. 结构化自检证据

每关完成或每轮交付时，产出一份可被离线回放消费的结构化自检证据；只定义格式与产出时机，供下游按证据回放，不在此做判定。

- 时机：垂直切片完成、每关结束、每轮创意迭代结束、收尾冷启动复验后各产出一份；随 checkpoint 一起保存，并登记到 `GOAL.md` 的 `completionEvidence`。
- 载体：项目根 `SELFCHECK.md`，或每关一个 `SELFCHECK-<关卡标识>.md`；用固定小标题 + 键值行或表格，便于机器读取。
- 字段：
  - 关卡 / 轮次标识与时间戳；
  - 关卡状态：可玩 / 未完成 / 阻塞，以及本关新增内容摘要；
  - 六维自检结论与证据引用：Overall、Gameplay、Graphics、Audio、Innovation、Theme Interpretation 各给结论（达标 / 待改进 / 缺失）与对应证据路径或引用（截图、读回值、音频播放证据、机制与主题对应说明）；任一维「缺失」不得判该关达标；
  - 素材创作记录：本关新增美术与音频资源文件、生成工具、引用路径与读回验证结论；
  - 冷启动 / 重开 / 暂停状态：三态各记一次实际运行结论与证据引用；
  - DEVLOG 决策点：本关 / 本轮的关键决策、取舍与下一步，引用 `DEVLOG.md` 对应条目（未建 `DEVLOG.md` 时直接写在此）。
- 只记可观察事实与证据引用，不凭印象补写，不写未发生的状态。
