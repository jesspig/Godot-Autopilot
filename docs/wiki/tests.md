## 架构总览

测试分两层，由根 `CMakeLists.txt` 的 `GDA_ENABLE_TESTS` 引入。该开关已固化在 `CMakePresets.json` 的 `base-debug`/`base-release` 基座（cacheVariables 默认 `ON`），并经 `inherits` 下发给全部 4 个可执行 configure 预设（`debug`/`debug-portable`/`release`/`release-portable`），**清理/重建 `build/` 后重新配置（`uv run main.py build` 或 `cmake --preset debug`）自动恢复测试目标，无需手动传参**；直接以裸 `cmake`（不带 preset）配置时仍为默认 OFF（`CMakeLists.txt:100`）：

| 层 | 目标 | 可执行文件 | 启动引擎 | 判定方式 |
|---|---|---|---|---|
| L1 | 纯单元测试（不触碰 Godot API） | `gda_unit_tests`（gtest） | 否 | gtest 断言，`gtest_discover_tests` 逐条注册到 ctest |
| L2 | 配置驱动引擎内测试 | `gda_test_runner` | 是（headless 编辑器） | C++ 执行器对 `call_tool` 响应做断言（`assert_engine.cpp`） |

L2 的链路：执行器自管 Godot headless 编辑器进程 → 注入 `GODOT_AUTOPILOT_PORT` → 经真实 MCP HTTP（`integration/mcp_test_client.cpp`，Streamable HTTP 传输）驱动领域工具，每 step 一次 HTTP 往返。**每份 `config/*.json` = 一次独立的编辑器生命周期最小闭环**（启动 → MCP 就绪 → before_all → stages → after_all → 停止），文件间不共享状态。

## 构建与运行

```powershell

# 构建
cmake --build --preset debug --target gda_unit_tests gda_test_runner

# 全量运行（ctest；L2 需 GODOT_PATH）
```

- **L2 依赖**：Godot 可执行文件。路径解析 `GodotProcess::resolve_godot_path()`（`godot_process.cpp`，grep `resolve_godot_path` 定位）：进程环境变量 `GODOT_PATH` 优先，为空才回退解析仓库根 `.env`；二者皆无 → 执行器退出码 2。

### CLI 与退出码（`tests/runner/main.cpp`）

参数：`--config-dir`、`--file`（可含或不含 `.json` 后缀）、`--headless|--gui`（互斥；用例 JSON 的 `headless` 字段优先）、`--no-auto`（不启动进程，端口取 `GODOT_AUTOPILOT_PORT` 直连外部 MCP）、`--keep-open`、`--report-dir`、`--help`。

退出码：0 全部通过；1 存在 FAIL/ERROR；2 参数或环境错误（含 `GODOT_PATH` 未配置、测试床未就绪——床内缺 `project.godot` 或缺 `addons/godot-autopilot/godot-autopilot.gdextension`，即尚未 `uv run main.py deploy`、`--no-auto` 端口未就绪、`--file` 无匹配、未捕获异常）。床校验在启动引擎前完成，把「床没部署」从约 90s 的 MCP 就绪超时压成秒级报错。

### 执行闭环（`godot_process.cpp`）

1. 随机空闲端口（`bind 127.0.0.1:0` 取回，`pick_free_port`）
2. 首次 `--editor --import` 幂等同步执行（120s 超时，失败/超时不致命，仅记日志）
3. 临时注入 `GODOT_AUTOPILOT_PORT` 后常驻启动 `--editor`（`--headless` 由用例决定；另注入 `GDA_FORCE_HEADLESS=1`）
4. 就绪轮询（200ms 间隔）：TCP 端口探测（connect 5s 超时）→ MCP `initialize` 握手（裸 `POST /mcp` JSON-RPC，响应含 `serverInfo` 即确认；读侧 5s 超时，服务器可能保持连接、超时退出而非挂死）
5. 执行 `before_all` → stages → `after_all`（`pipeline_executor.cpp`；`before_all` 失败即整体 `fatal_error`；`before_all`/`after_all` 为 plain 步骤不支持 expect 断言，`after_all` 工具报错不改变整体判定（仅进程死亡导致跳过时补 `fatal_error` 说明）；stages 失败按 `on_failure` fail_fast/continue）
6. 停止：`taskkill /PID` 软杀 → 5s 宽限 → `TerminateProcess` 兜底；崩溃时附编辑器日志（`pipeline_executor.cpp` 的 `CRASH_LOG_LIMIT` 截断至 2000 字符）

stdout/stderr 各接独立管道读线程持续消费，防 64KB 缓冲写满阻塞子进程。

### 报告（`runner_report.cpp`）

- 控制台表格：文件名称 / 通过步骤数 / 耗时（<10s 显毫秒，否则显秒）/ 状态 `PASS|FAIL|ERROR`（`fatal_error` 非空 → ERROR）
- JSON 报告：`tests/output/report-YYYYmmdd_HHMMSS.json`，字段 `generated_at` / `total_files` / `passed_files` / `files[].{name,passed,duration_ms,fatal_error,steps[]}`

**JSON schema 冻结规则**（`config_loader.cpp` 强制校验，违规抛 `runtime_error` 且错误消息含字段路径）：顶层必填 `name`/`pipeline`；`headless` 默认 true；`requires` 可选（capability string 数组，白名单 `{process, code_execute, game_runtime, destructive, user_tools, read, write, all}`，逐元素校验非空与白名单、拒绝重复元素；空缺时执行器注入哨兵 `GODOT_AUTOPILOT_ALLOW=none` 即默认拒绝态，各用例的声明清单见 L2 表）；`on_failure` 仅 `fail_fast`（默认）| `continue`；`before_all`/`after_all` 仅 tool+args+id（不支持 traverse/expect）；`stages[].steps` 平铺保留顺序；步骤 `tool` 与 `traverse` 二选一；`traverse.kind` 仅 `domain_tools`；`traverse.mode` 仅 `empty_args`（默认）| `heuristic_smoke`；`args` 值任意 JSON、嵌套原样保留；步骤可选 `soft_error`（字符串，错误文本前缀，见下「断言语义」的软失败条）；**未知字段拒绝**：顶层、`pipeline`、stage、步骤、`expect`、`field_checks` 元素六层均为封闭白名单（见 `tests/README.md` 第 6 节规则 10），白名单外键即抛错；**空 expect 拒绝**：`expect` 存在时 `has_keys` 与 `field_checks` 至少其一非空。

**断言语义**（`assert_engine.cpp`）：`has_keys` 顶层键存在性；`field_checks[].key` 点路径分段查找（仅对象点路径，不支持数组下标；任一段缺失判失败）；`value` 数值兼容（int/double 统一转 double）；`not_empty`（string 非空 / array、object `Size()>0` / null 判空失败）；无 `expect` 时仅检查 `last_call_was_error()` 为假（即工具调用未报错）；**有 `expect` 的步骤在断言通过后隐式断言响应顶层无 `error` 字段**（`pipeline_executor.cpp` 的 `run_single_step`），`allow_error=true`（`expect` 层或 `field_checks` 元素级声明，取或）豁免该断言，`before_all`/`after_all` 无 expect 路径维持仅查调用未报错。

**软失败语义**（`pipeline_executor.cpp` 的 `apply_soft_failure`，2026-10-21 新增）：步骤声明 `soft_error` 后，若该步失败且工具响应的 `error` 文本以该前缀开头，则记为**软失败**——步骤 `passed` 仍为 false，但另置 `soft_failed=true` 与 `soft_reason`（文件级汇总 `soft_failures` 计数，控制台以 `~` 行标注），且**不置 `fatal_error`、不计入文件失败**（before_all 软失败不中断流水线，stages 软失败不置 `all_steps_passed=false`）；错误文本不匹配的失败、期望不匹配、编辑器进程死亡等仍判**硬失败**。用途：把「环境边界导致的必然失败」与「真实回归」区分开，既不让用例被环境边界 fatal，也不掩盖断言本身的回归。当前仅 `38_csharp_bridge.json`（10 步）与 `44_csharp_tooling.json`（1 步）使用。

## 全量遍历（`traversal.cpp`）

- **工具来源（运行时枚举）**：遍历经 `search_tools` 空 query 枚举全部 catalog 工具名（`list_tool_names`），响应形如 `{"results":[{"name","score"},...]}`；**452 条 = 451 域工具 + `system_status`**（`traversal.cpp:25` 的基线常量 `kBaselineEnumerated = 452`），跳过 7 个协议级元工具；解析失败（非 JSON 对象/缺 results 数组/清单为空）抛 `std::runtime_error`
- **排除判定**：每工具先 `get_tool_detail`（响应含 `side_effect`/`mutating`/`dynamic` 字段），`side_effect` 非空且**非 `"none"`**（判据见 `traversal.cpp:23` 的 `kSideEffectNone` 与 `:443-444` 的 `has_side_effect`；只读工具回显 `"none"` 不算有副作用）/ `mutating=true` / `dynamic=true` 任一命中即记录 excluded 并跳过（不再解析源码、不再硬编码名单；动态工具在日常 L2 无注册，`dynamic` 分支为防回归保留）；再校验存在性与工具名一致性（响应非对象或名字不匹配 → FAIL）
- **`empty_args`**：空对象调用；响应非 JSON 对象 → FAIL；含 `error` 字段算"有错误响应"（统计 error 数）；**若该错误的错误文案命中预期错误标记表则豁免为通过，否则判失败**（见下「错误判失败与预期错误豁免」）；schema `required` 非空但空参未报错 → 记 **warnings**（不 FAIL）
- **`heuristic_smoke`**：按 schema properties 类型生成启发值（integer→0、number→0.0、boolean→false、array→`[]`、object→`{}`、其余→`"test"`）；无 properties 的工具跳过（不产生步骤）；错误判定与豁免同 `empty_args`
- **崩溃检测**：每步调用后查编辑器进程存活，进程死亡 → `fatal_error`（附 2000 字符日志）
- **基线断言**：`traversal.cpp:326-362` 的 `compare_baseline` 对每种模式逐项比对 `enumerated` / `excluded` / `candidates` / `warnings` / `calls` 与基线常量（452 / **177** / **275** / **0** / **275**（`empty_args`）/ **221**（`heuristic_smoke`）；`warnings` 在 `empty_args` 与 `heuristic_smoke` 两种模式下均断言为 0），任一不符即记入 `baseline_diffs` 并判失败；基线可由环境变量 `GDA_TRAVERSAL_BASELINE_EMPTY_ARGS` / `GDA_TRAVERSAL_BASELINE_HEURISTIC_SMOKE` 临时覆盖（各 5 个逗号分隔的非负整数：`enumerated,excluded,candidates,warnings,calls`），失败信息含基线来源与授权提示
- 统计输出：调用总数 / 通过 / 失败 / result / error / "missing required" / 跳过（无 properties）/ 排除（副作用/可变/dynamic）/ 豁免错误数

### 错误判失败与预期错误豁免

## 守卫与脚本项（tests/guard/ + tests/scripts/，ctest 常驻）

- `migration_guard`（`migration_guard.cmake` + `migrated_domains.txt`，30 域 + `strict`）：零依赖源码断言，防旧宏/`schema_*_ops.cpp`/`tool_input_schema` 回退；实测输出 `-- [migration-guard] OK (domains: 30, strict: on)`；迁移规则见 [ToolSpec 数据层与执行管线](tool_base_design.md)。
- `comment_guard`（09-19 注释清理批新增，`comment_guard.py`）：递归扫描 `src/` 与 `tests/` 下 `*.cpp/*.hpp`（`SCAN_DIRS`，只认这两棵目录的 C++ 文件，仓库其它位置的 `.md` 不在范围内），除 `// namespace` 结尾标记外禁止任何 `//`/`/*…*/` 注释（正确处理字符串/字符字面量与 `R"TAG(…)TAG"` raw string）；无违规打印 `comment-guard OK` 并退出 0，违规退出 1，文件无法解码退出 2；判定时机为 ctest 而非编译。
- `main_thread_guard`（10-20 新增，`tests/guard/main_thread_guard.py`）：**主线程契约守卫**，静态扫描 `src/` 下 `*.cpp/*.hpp` 里的 **Godot API 直接调用**。判定依据是「线程上下文分类」——每个源文件被显式归入主线程（`main`）、受管（`managed`）或外线程（`foreign`）三类（`THREAD_CONTEXT_RULES`），外线程文件里的 Godot API 调用默认违规，只有落在该文件显式登记的主线程作用域里才放行（`FOREIGN_MAIN_THREAD_SCOPES` 作用域级豁免表，当前只登记 `src/core/log_persist.cpp` 的 6 个主线程作用域）。词法顺序：先剥离字符串字面量（含转义）、字符字面量与 `R"TAG(…)TAG"` raw string，再剥离注释，最后做标识符匹配（`GODOT_API_PATTERNS` 覆盖 `godot::FileAccess` / `DirAccess` / `EditorInterface` / `Engine` / `SceneTree` / `ClassDB` / `ProjectSettings` / `Input` / `DisplayServer` / `OS` / `Performance` / `Resource` / `ResourceLoader` / `ResourceSaver` 等）。**退出码语义**：0 = 无违规（打印 `main-thread-guard OK`）、1 = 有违规（逐行打印 `文件:行号: 片段`）、2 = 文件读或解码失败；可选参数是待扫描目录，缺省为仓库 `src/`；只用标准库，判定时机为 ctest 而非编译。
- `version_sync_guard`（10-17 新增，`guard/version_sync_guard.py`）：版本号一致性——扫描 `skills/` 下全部文本文件与根 `README*.md`，其中每一处版本钉都必须与根 `VERSION` 同值，另含 `VERSION` 与 `CLI_VERSION` 两个值源；非版本引用（如 `#develop`）只登记、不参与比对。退出码语义：0 = 全部一致、1 = 存在版本漂移（逐条打印 `文件:行号 = 值 (标签)`）、2 = 关键文件缺钉 / 未知引用形态 / 文件读失败。覆盖范围以守卫脚本为准，详见上文 CLI 小节。
- `cli_contract`（10-17 新增，取代 09-25 的 `skill_scripts`，`tests/scripts/test_cli_contract.py`）：CLI 契约 mock conformance（驱动 gda CLI `gda.ts`），详见上文 skill_gen 小节。

## L2 环境漂移（编辑器场景恢复）

当工程 `project.godot` 含 `run/main_scene` 且 `.godot/editor` 缓存记录最近场景时，headless 编辑器启动后会**异步恢复主场景**，覆盖用例 `before_all` 创建的 Root 场景，导致 `01_scene`/`02_property` 等失败。测试床定义里不含 `run/main_scene`，且床内没有任何 `.tscn`，这条竞态由构造消除（历史上 Example 时代 7 份同批失败的记录见 [changelog/2026-09-18-log.md](changelog/2026-09-18-log.md)）。

仍会遇到的残留是 `.godot/editor/editor_layout.cfg` 的 `open_scenes`：用例（如 `06_move_references`）在 `after_all` 删掉场景后，这条记录仍指向已不存在的 `res://gda_tmp_*` 路径，下次编辑器启动会尝试打开并报缺失文件。批量同因失败时先查 `tests/testbed/.godot/editor/editor_layout.cfg` 有无残留 `open_scenes`，再核对插件与用例代码——`.godot/` 属生成物，删掉即恢复（`main.py clean` 会连 `addons/` 一起清，清后须重新 `deploy`）。

## 已知遗留（待跟进）

- **编辑器进程的引擎错误不可经 MCP 观测**：`user://logs/godot.log` 只由**游戏进程**按工程 `debug/file_logging` 写（`src/tools/system_tools.hpp` 的 `get_game_log_entries` 自述要求"先启动游戏"，`skills/godot-autopilot-runtime/references/debug-paths.md` 同口径），headless 编辑器即使把 `debug/file_logging/enable_file_logging` 置真也不产生该文件（09-26 在测试床上实测：当时床目录内只有 `user://godot_autopilot/{logs,traces}`，无 `user://logs`；10-21 起日志与轨迹目录已迁至集中根的工程目录 `<集中根>/projects/<项目名>-<路径哈希前 8 位>/{logs,traces}`）。`get_debugger_log` 读的是编辑器进程缓冲，但响应是单个文本串、无 `filter`/`matched_lines`，断言引擎也表达不了"不含某子串"。因此 `22_uid_guard` 原 ⑤ 的两道引擎错误守卫已删除；恢复它需要能力改动（插件注册引擎 logger + `get_debugger_log` 增过滤与计数），不要把它当作已覆盖项。
- **mcp-cpp-sdk 客户端偶发响应等待缺陷（未修复，待跟进）**：L2 执行器（`tests/integration/mcp_test_client.cpp`）在 runner 场景下对特定响应的等待偶发退化为约 60s（现场约 50% 触发）；同一时刻服务端对独立请求完全健康，指向 SDK **客户端**侧响应分发/匹配缺陷。本轮在测试侧规避（移除触发步骤 + `call_tool` 的 transport 错误重试 + L1 消息断言），SDK 侧根因待跟进——不要按"已修复"处理。
- **游戏侧新增路径未做 L3 双进程 E2E**：`queue_game_input` 的 wheel/mouse_motion、`click_game_ui_element`（09-16 起含 `window_position` 窗口坐标换算）、`capture_game_viewport` 的 region/max_dimension/annotate 在游戏进程内执行，本轮验证范围为编译通过与代码级路径检查，未编写编辑器 + 游戏双进程的 L3 端到端用例。`click_game_ui_element` 的换算端到端断言（320x180 视口 → 1280x720 窗口 4x 下 `window_position={640,360}`）留待示例游戏恢复后补测，补测骨架见 `23_click_ui_coords.json` 的覆盖力声明；换算正确性现由 L1 `game_ui_coords_test` 覆盖。`35_scene_tree_gate` 只覆盖无游戏进程时的编辑器侧门禁与编辑器树未被触碰，8 个 SceneTree 工具在真实游戏进程内的行为（暂停/重载/组调用与通知/计时器创建）未覆盖；`37_game_ready_gate` 的就绪窗口（peer 已连接但 `gda:ready` 未到）排队与重放同样留待真实游戏进程复现验收（决策逻辑由 L1 `ready_policy_test` 覆盖）。
- **编辑器 UI 动作未自动化**：L2 执行器不支持跨步骤变量引用（上一步返回的元素 path 无法传给下一步），`click_editor_element` / `type_editor_element_text` 的真实点击/输入未纳入自动用例；`10_editor_input` 仅覆盖参数校验错误路径（在注入前返回 error，无副作用）。
