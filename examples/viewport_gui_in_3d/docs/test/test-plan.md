# 测试计划

本文规定本工程作为 **godot-autopilot（GDA）MCP 插件测试床**时的测试目的、目标、约定、证据要求与记录规范。本演示已完整实现，测试以**编辑器内验证**为主，不做开发增量。

## 测试目的

通过“在编辑器里打开、运行并点透一个 3D 中的 2D 界面”这一真实任务，评估 GDA 能否让 AI 客户端**仅凭本文档集与磁盘文件**完成验证，重点考察 GDA 的**视口截图能力**与 **UI 点击能力**，并客观记录工具与文档的实际表现。

## 测试目标（评估维度）

1. **视口截图能力**：GDA 能否抓取编辑器视口与运行画面，并支撑“面板是否成像、布局是否正确”的判断。
2. **UI 点击能力**：GDA 能否把点击/输入动作投递到 3D 中的 GUI 控件（按钮、输入框、滑杆、下拉框），并读回可见反馈。
3. **工具可用性**：各工具能否完成其宣称的功能；失败时错误信息是否可操作；工具描述与 Skill 文档是否与实际行为一致。
4. **工具完备性**：完成本验证所必需的能力是否存在；缺失时是否存在可接受的替代路径。
5. **文档自主性**：本文档集是否只描述“是什么/怎么验”；是否存在误导验证的内容（错误路径、矛盾数值、含糊验收）。
6. **真实交付**：结论基于真实发生的编辑器事件与截图；不接受“看起来通过”。
7. **机制可读性**：AI 客户端能否仅凭文档与 `gui_3d.gd` 只读内容讲清转发链路（直投 vs 换算分支）。
8. **记录规范**：问题记录包含五要素（见下）；表现优秀处同样如实记录；不夸大、不贬低。

## 测试约定

- 验证动作**仅通过 GDA 完成**（打开场景、运行、截图、点击、读回）；允许以只读方式查阅工程文件用于核对。
- **不主动重启 Godot 引擎**；若引擎意外崩溃，如实记录现象并结束本轮测试。
- 所有结论必须基于实际发生的事件；证据随测试报告留存。
- 测试期间不更新本仓库的 wiki 内容；不改动 `docs/` 之外的任何文件。
- 本演示无存档，不存在删档/恢复流程。

## 验证循环执行法

验证按人类式小循环推进：**开场景 → 做动作 → 截图核对 → 记结论**，往复循环；禁止一次性做完所有点击、最后再统一补截图。

### 四拍

| 拍 | 名称 | 要求 |
|---|---|---|
| 1 | 开 | 只打开本环需要的场景（主场景或面板场景），确认场景树结构与文档一致 |
| 2 | 做 | 只做本环的一个动作（一次点击/一次输入/一次拖动），不提前做下环的动作 |
| 3 | 看 | 截图：编辑器视口核对结构，运行画面核对反馈；截图即证据 |
| 4 | 记 | 本环一句话记录：做了什么、截图看到了什么、过还是没过 |

### 铁律

1. **单循环只验一个验收点**：多个点的步骤不得合并到同一环。
2. **失败只定位本环**：先查动作是否投递到位，再查文档描述是否准确，不扩大范围。
3. **截图与验收项一一对应**：报告中标注每张截图对应的场景编号（A–G，见 [acceptance.md](./acceptance.md)）。

### 循环切分

| 环 | 开 | 做 | 看（验收） |
|---|---|---|---|
| 1 | 主场景 `gui_in_3d.tscn` | 打开并运行 | A：场景结构 + 首帧成像 |
| 2 | 主场景 | 悬停/离开面板 | B：悬停态出现与清除 |
| 3 | 主场景 | 点击按钮 + 输入框打字 | C：点击与文本反馈 |
| 4 | 主场景 | 拖横/竖滑杆 + 下拉选中 | D/E：拖动与弹窗 |
| 5 | 主场景 | 等待动画半程后截图 | F：透视变化（真 3D 证据） |
| 6 | 面板场景 + 配置 | 只读核对 | G：结构与配置一致性 |

## 证据要求（含截图）

**逻辑断言不是完整证据；涉及成像与交互的验收必须看图。**

| 验收类型 | 必须提供的证据 |
|---|---|
| 逻辑行为（分支归属、通知成对、幂等回退） | 运行日志或可读回的状态值（截图可选） |
| **结构核对**（场景树、节点属性） | **编辑器界面截图**：视口 + 场景树/检查器（展示结构与位置） |
| **成像效果**（面板贴于 Quad、文字可读、色彩保真） | **运行画面截图**：与 `screenshots/gui.png` 同视角比对 |
| **交互反馈**（按钮按下、输入上字、滑杆跟手、弹窗展开） | **运行画面截图**：动作前后各一张，控件与 Quad 同框 |
| **真 3D 性**（随相机透视变化） | **运行画面截图**：动画不同相位至少两张 |
| **配置核对**（主场景、主题缩放、物理层、渲染器） | 只读读回的配置值（截图可选；注意区分源库原件与工作树最小模板） |

截图证据随测试报告归档（如 `report/img/`），并在报告中标注每张截图对应的验收场景编号。

## 问题记录格式

每个问题必须包含：

1. **触发场景**：在做什么时发生；
2. **详细操作步骤**：可复现的步骤序列；
3. **预期行为**：文档或工具声称的行为；
4. **实际表现**：真实观察到的结果（附证据）；
5. **问题分析**：基于事实链的推断，无法定位根因时如实说明边界。

## 终止条件

- 若因 GDA 的功能缺失或致命缺陷导致验证无法继续，可基于事实终止验证并转入报告编写。
- 引擎崩溃不尝试重启；记录现象并结束本轮测试。

## 输出

- 测试报告：`report/<YYYY-MM-DD-HH-mm>-report.md`（仓库根目录的 `report/`，非本文档目录）。
- 报告应包含：工具与文档的总结性评估（重点单列视口截图与 UI 点击两项能力）、按优先级排序的优化建议、以及全部问题记录与证据索引。
