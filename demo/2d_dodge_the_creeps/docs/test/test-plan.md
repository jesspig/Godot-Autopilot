# 测试计划（GDA E2E 测试床）

## 测试目的

通过“导航 → 读码 → 运行 → 截图”一个已建成小游戏，评估 GDA MCP 插件在真实工程上的端到端能力，并客观记录工具与文档的表现。

## 测试目标（评估维度）

1. **导航**：能否定位 4 场景 / 4 脚本 / 关键节点（`StartPosition`、`MobPath`、三个 Timer、HUD 三件套）。
2. **读值可信**：读回的节点属性、信号接线、输入映射是否与 `.tscn` / `project.godot` 文本一致。
3. **运行验证**：能否启动运行、按键移动、刷怪、计分、Game Over、重开。
4. **截图证据**：编辑器结构截图与运行画面截图是否按验收项留存。
5. **文档自主性**：本 docs 是否只记录现状、有无误导或编造。
6. **配置恢复**：工作树 `project.godot` 缺失段的恢复过程是否可记录、可复验。
7. **记录规范**：问题记录含五要素（触发场景 / 步骤 / 预期 / 实际 / 分析）。

## 测试约定

- 游戏逻辑文件（`*.tscn`、`*.gd`、`project.godot`）**只读**，除非测试任务明确要求恢复配置；任何写操作记录改了什么、为什么。
- **不运行构建**（本工程无构建步骤）；不修改 `docs/` 之外无关文件。
- 所有结论基于实际发生的事件；证据随报告留存。
- `docs/` 本身是测试对象，发现文档与源码不一致时以源码为准并记录。

## 前置检查

1. 确认 `project.godot` 是否含 `[input]` / `[display]` / `[rendering]` 段；缺失则先按源库原件恢复并记录。
2. 确认主场景为 `main.tscn`（`run/main_scene` 以源库原件为准）。

## 执行法（每项：找 → 读 → 跑 → 截图）

| 步 | 动作 |
|---|---|
| 找 | 用 GDA 定位场景/节点/脚本 |
| 读 | 读回属性或代码片段，与本 docs 交叉核对 |
| 跑 | 运行 `main.tscn`，按验收项按键操作 |
| 截图 | 编辑器结构或运行画面截图存档，在报告中标注对应验收项 |

## 证据要求

| 验收类型 | 证据 |
|---|---|
| 结构（节点、接线、配置） | 编辑器界面截图（视口 + 场景树/检查器）或可读回的属性值 |
| 运行行为（移动、刷怪、计分、结束、重开） | 游戏运行界面截图；在真实运行中抓取 |
| 菜单/HUD 三态（标题 / Get Ready / Game Over） | 运行截图每态至少一张 |
| 观感 | 与 `screenshots/dodge.png` 同框对比说明 |

逻辑断言不是完整证据；涉及画面效果的验收必须看图。

## 问题记录格式

1. 触发场景；2. 详细步骤；3. 预期行为；4. 实际表现（附证据）；5. 问题分析（无法定位时如实说明边界）。

## 终止条件

- 引擎崩溃不尝试重启（按仓库协作惯例如实记录并结束本轮）。
- 因 GDA 缺失能力无法继续时，基于事实终止并转入报告。

## 输出

- 测试报告：`report/<YYYY-MM-DD-HH-mm>-report.md`（仓库根 `report/`，非本目录），含评估结论、优化建议、问题记录与证据索引。
