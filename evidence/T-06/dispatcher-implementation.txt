二、GCP 分发状态机（DispatchState）
  idle          初始态，或收到帧后复位
  auth_ignored  looks_like_auth_frame 命中（JSON-RPC initialize / jsonrpc 字段 / gda_token），
                不解码、不回包，token 不进入业务 envelope
  decode_failed JSON 解析失败（严格重复键策略）→ 返回 error(result_unknown)
  validation_failed 版本/实例/种类/envelope 校验或未知方法失败 → 返回对应结构化错误
  duplicate_rejected request.id 已完成（写出过）→ error(result_unknown)，不重新执行
  dispatched     校验通过并路由到 ControlService 子服务
  awaiting       异步 call.start：pending + task_id，任务落入 JobService，交还 in-flight 给 waiter
  terminal       已产出响应 envelope（ok / error / needs_confirmation / pending）

转换策略：
  收到帧 → 先判认证首帧 → auth_ignored；否则 decode → decode_failed；
  否则做版本/实例/种类/validate_envelope 校验 → validation_failed；
  否则查 completed_ 去重 → duplicate_rejected；否则 routed → dispatched；
  子服务产出响应 → terminal；异步 pending → awaiting → waiter 主线程 finalize 任务。
  每个产生响应的分支把 request.id 写入 completed_；重复 id 一律 result_unknown 且不重发。

三、方法到 ControlService 的映射
  hello / capabilities.get → gcp::default_capabilities + negotiate_capabilities
  catalog.list/search/describe → CatalogService
  call.start / call.confirm / task.cancel → InvocationService（sink 注入，confirm 使用原请求参数摘要）
  call.get / task.get / task.list → JobService
  events.subscribe / events.resume → EventService + 有界 outbox
  trace.get → TraceService
  所有 Godot API 仍由 sink 经 transport->submit（SDK/CommandQueue）到主线程；waiter 只在后台等待，
  finalize 通过 queue.submit 回主线程，无 execute_sync、无 transport 线程直接调用 Godot API。

四、安全与契约保持
  复用 4 字节长度前缀（ipc_framing）、4 MiB 帧、8 连接、16 在途、10 分钟空闲超时（常量未改）。
  token 只在 transport 认证层出现；dispatcher 从不把入参 params 回显到响应，响应只带产出 result；
  额外对 token/secret/password/credential/api_key 类参数键做输入过滤，避免进入 InvocationRequest 与工具参数。
  事件 outbox 软限 64 / 硬限 256，用 gcp::classify_backpressure 判定，硬限时拒绝发布并返回
  backpressure_exceeded。
  认证失败沿用 transport 的关连接路径，不回退 HTTP。
  MCP JSON-RPC/SDK 路径保留为 parity：仅 looks_like_gcp 为真时走 GCP，其余帧仍走原 MCP 路径。

八、风险与待办
  - 未编译验证：GcpInvocationSink 的异步桥、lambda init-capture 与 JsonValue 用法需主代理统一构建确认。
  - 实例记录 endpoints.ipc.protocol 仍为 "mcp-jsonrpc"（刻意保留，避免改动 CLI 发现逻辑）；
    切换到 "gcp" 应与 CLI/Skills 改造协同，属于后续任务。
  - line handler 同时承载 GCP 与 MCP parity；GCP 请求的 in-flight 在 awaiting 时移交 sink waiter，
    需确认 stop() 先 cancel/join waiters 再析构 jobs 的顺序（已按此顺序接入）。
  - call.confirm 使用 call.start 保存的原请求参数摘要；若客户端随后修改参数语义，应与摘要契约对齐。
  - 事件 outbox 为进程级而非每连接级硬限；多连接共享时需主代理评估是否按连接拆分。
